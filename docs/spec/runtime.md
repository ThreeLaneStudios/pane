## §36.0 Purpose and the OpenClaw boundary

**User story.** Your agent in Pane works like a runtime. It takes on big jobs, works on a schedule, delegates to other agents you've made, and reaches you when it has something — whether it runs on an API model or on OpenClaw.

Today an API-runtime agent (Anthropic, OpenRouter, Venice, Ollama) does only what fits in one turn, only when the user starts it. OpenClaw supplies continuation, scheduling and spawning for OC agents. This section gives API agents the same shape inside Pane, without touching how OC agents work.

### §36.0.1 The boundary, stated once

**OpenClaw agents keep OpenClaw's runtime. Pane's runtime is for API agents.**

**OC-native work — shell commands, local file access, OC's own memory — stays OC's own cron, never a Pane job.** A Pane job on an OC-bound agent gets exactly the Pane tool surface §36.3.7/§36.5 define: Pane's notes/tasks/schedule tools, nothing OC-specific. An agent that needs shell, files, or OC memory on a schedule keeps using OC's own cron, outside Pane entirely — that boundary doesn't move. This is the line C28(b) draws: Pane is the toolset for Pane jobs; OC's own tools remain OC's own scheduler's business.

Every feature below is tagged with one of two modes, and the tag is the contract:

| Mode | Meaning | Mechanism |
|---|---|---|
| **API-only** | Offered to, and run for, sessions bound to an agent with `runtime_type ∈ {anthropic, openrouter, venice, ollama}`. Never for `openclaw`. | Same allowlist shape as the web-tool gate (`tools.rs:989-993`, ADR-0064 D3): an allowlist of runtimes, not an `openclaw` denylist. |
| **Read-side** | Pane ingests what OC already produced. No new writes into OC. | §30.11 ingestion command, dedupe by id/seq (#3055). |

| Feature | Mode |
|---|---|
| §36.1 Loop extraction | API-only (refactor of `ai_chat_stream`, which OC turns also pass through — behaviour-preserving, see §36.1) |
| §36.2 Auto-continue | API-only |
| §36.3 Scheduler | **Allowlisted to every runtime, API and OC alike — both the loop and the dispatch (C28(b), #3129).** A job on an OC-bound agent dispatches exactly like a job on any other agent: `prepare_job_dispatch` resolves its `AiProvider::OpenClaw` config the same way an interactive OC turn's does, and `run_agent_loop` runs it with Pane's tool surface (§36.3.7, §36.5), minus the API-only web/attachment tools (§36.0.1 — OC agents have their own file access). There is no separate OC-side session for a job and no `sessions.send`/`sessions.create` call anywhere in this path. **Auto-continue stays API-only** (§36.2, unaffected). **`spawn_job` stays API-only as a target restriction** (§36.4 — an OC agent still cannot be `spawn_job`'s target, and OC's own spawns stay OC's `sessions_spawn`; unaffected by this ruling, which is scoped to the scheduler alone, same scoping Ruling 2 already established for the tool-offer half). |
| §36.4 Spawn | API-only (OC spawns stay OC's `sessions_spawn`) |
| §36.5 Proactive turns that act | API-only |
| §36.6 Background OC pickup | Read-side |
| §36.7 Notifications | Both (emitted by Pane in every case) |
| §36.8 Report-back | API-only for Pane jobs; read-side for OC spawns |

**Things this spec never does:** call an OC method outside the nine in §22C.7.1; disable or configure OC's own cron (it can only be disabled globally, so Pane leaves it alone); run `ai_chat_stream`'s loop for an OC-bound session beyond what it does today (one gateway round-trip per turn); write to `~/.openclaw`.

## §36.1 Loop extraction (#3059) — the guard before the change

> **Status: BUILT** (PR 1, #3059). `ai_chat_stream` is now a thin wrapper that builds one `AgentLoopInputs<R: tauri::Runtime>` and spawns `run_agent_loop(inputs)` — the loop body moved verbatim. `stream_anthropic`/`stream_ollama` (and, discovered during the build, `execute_single_tool` and its own `AppHandle`-carrying callees) are generified the same way `stream_openrouter` already was, so `run_agent_loop` compiles and runs under `tauri::test::mock_app()`'s `AppHandle<MockRuntime>`. The real-loop regression test (§36.1.4) replaces the #3058 mirror. `TurnOrigin` (§36.11) is introduced as a field on `AgentLoopInputs`, constructed once today (`ai_chat_stream`, as `TurnOrigin::User`); the scheduler tick is PR 2's job, not yet built. §36.2/§36.3's `continue_policy`/`job_id`/`cancel` fields are deliberately NOT added to `AgentLoopInputs` in this PR.

**Mode:** API-only. **PR 1 of the sprint. Nothing else in this spec lands before it.**

### §36.1.1 Why first

#3058 replaced the fixed loop clock with a no-progress timeout. Its core regression test ("a job that keeps making progress past the old 120 s is not cut off") could not drive the real loop: `ai_chat_stream` takes a concrete `tauri::AppHandle` (Wry), and Tauri's only test harness yields `AppHandle<MockRuntime>`. The shipped test is a mirror that calls the real `check_no_progress_timeout` (`ai::chat`) but hand-rolls the reset. Reed's mutation audit (`docs/audits/2026-10-21-pr-3058-no-progress-timeout.md`) showed that deleting either production reset site leaves all tests green.

Auto-continue (§36.2) rewrites this loop. The reset wiring must be under test before that happens.

### §36.1.2 Production shape to preserve (verified at `44c1ae18`)

Inside `ai_chat_stream`:

| Site | Role |
|---|---|
| `let mut last_progress = Instant::now();` | init — right after `let mut iteration = 0;` and the `#3053 D+E` comment block explaining the reset convention, immediately before `let idle_timeout = Duration::from_secs(idle_timeout_seconds);`. Sets the loop's first no-progress baseline, before the loop body runs. |
| `if check_no_progress_timeout(last_progress, idle_timeout)` | the single check — top of the `loop { … }` body, immediately after the `iteration += 1; if iteration > max_iterations { … }` cap check and before this iteration's provider call. Runs once per iteration, never mid-call. |
| `last_progress = Instant::now();` (reset 1 of 2) | inside `if !final_text.trim().is_empty() { … }`, right after `accumulated_text.push_str(&final_text);`. Fires when the model's response contains new, non-empty text — comment above it: "#3053 D+E — progress reset 1 of 2". |
| `last_progress = Instant::now();` (reset 2 of 2) | right after `current_iter_start = full_messages.len();`, before the assistant message carrying this iteration's tool calls is built. Fires when this iteration's batch of tool calls has finished — success, tool-level error, or gate refusal all count as finished — comment above it: "#3053 D+E — progress reset 2 of 2". |
| `max_tool_iterations` read | per-turn ceiling — `let max_tool_iterations: u32 = db.0.lock()…`, under the `§4.5.2` comment ("read max_tool_iterations from ai_settings"), right after `dispatch_agent_name_for_done` is cloned, before the loop starts. |
| `"Reached the {}-tool-call limit for this turn…"` | limit exit message — **not** in `ai_chat_stream`; the `AgentExitKind::IterationCap` match arm inside `build_stop_fallback_message`. Must stay distinguishable from the `NoProgressTimeout` arm's wording in the match arm immediately below it. |

### §36.1.3 Scope

1. Extract the loop shell into `run_agent_loop<R: tauri::Runtime>(…)`, following the generification #3058 already applied to the dispatch call. `ai_chat_stream` becomes a thin wrapper that builds the loop inputs and calls it.
2. The loop's inputs are a struct, not a parameter list — §36.2 and §36.3 add fields (`continue_policy`, `job_id`, `cancel: Arc<AtomicBool>`), and a struct keeps those additions out of every call site.
3. Add the real-loop regression test: fake model producing progress past the old 120 s, controllable clock, no real waits. Assert not cut off, and terminates normally.
4. Delete the mirror in `ai/timeout_tests.rs`.
5. Ship the `syn`-based AST gate (ADR-0016) enforcing the `TurnOrigin` invariant (§36.11): CI fails if `TurnOrigin::User`/`TurnOrigin::Job` is constructed outside `ai_chat_stream` and the scheduler tick.

### §36.1.4 Tests (gate for PR 1)

- The new test **fails at pre-#3058 code** (splice onto a base without the fix; confirm red).
- **Amended for #3050 PR 3 (Matt's Ruling 1, 2026-10-27):** deleting the reset-2 mutation (the unconditional `last_progress = Instant::now();` after the tool-call batch) is the one that must turn this test red. Deleting reset-1 (the text-accumulation reset, `if !final_text.trim().is_empty() { last_progress = Instant::now(); }`) does **not** turn it red, and that is correct, not a gap: PR 3 (auto-continue) proved reset-1 is never load-bearing on its own, because the only way to skip reset-2 is `tool_calls.is_empty()`, and that path unconditionally ends the turn as Done — there is no continuation path where reset-1 fires alone, since auto-continue only re-enters the loop when tool calls WERE produced (which always takes reset-2). **Reset-1 stays in the code as defensive, not dead — it is the half of "no tool call finished, no new text" that stands on its own the moment a future change lets the loop continue without a tool call (a text-only "keep writing" continuation).** No PR number is attached to that future change; it is not deferred work on anyone's list, just the condition under which reset-1 would start mattering.

- **No functional change.** Full retest ahead of it — this is why it sits at the start of a sprint, not before a release.

## §36.2 Auto-continue

> **Status: BUILT** (PR 3, #3050). `run_agent_loop` self-continues via an in-place `continue` of its own `loop { .. }` (not a second async call) once `max_tool_iterations` (now a checkpoint interval, Ruling 4) is hit, gated on the model's last iteration having produced tool calls, the `API_RUNTIME_ALLOWLIST` (`ai/runtime_constants.rs`, never `openclaw`), and `job_ceiling_tool_calls` budget remaining. `AgentLoopInputs` gains `continue_policy: Option<ContinuePolicy>` and `cancel: Arc<AtomicBool>` — the two fields PR 1 left out. `AgentExitKind::IterationCap` is retired (Ruling 2); `Stopped`/`Ceiling` land with §36.2.1's exact copy. `stop_turn` (new command) and a per-session `CANCEL_FLAGS` registry (`OnceLock<Mutex<HashMap<String, Arc<AtomicBool>>>>`, same shape as the existing `IMAGE_CACHE`) back the Stop button. `load_chat_messages` and `maybe_compact_thread`'s message-fetch queries now `SELECT synthetic, continued`.

**Mode:** API-only.

### §36.2.1 Behaviour

When a turn hits `max_tool_iterations` and the model's last iteration **still produced tool calls** (the loop's own signal that work remains — not a model self-report), Pane starts the next turn itself instead of posting the "ask me to continue" message:

1. Append the limit-exit text to the transcript as an assistant message, flagged `continued = 1` so the UI can render it as a progress divider rather than a stop.
2. Append a synthetic user message `"Continue."` (not shown in the UI; `role = 'user'`, `synthetic = 1`).
3. Re-enter `run_agent_loop` with the same session, the same `max_tool_iterations`, and the **job ceiling** decremented by the tool calls used so far.

The turn ends when one of these fires, in this priority:

| Exit | Signal | Message |
|---|---|---|
| Done | an iteration produces no tool calls | normal end |
| Stopped | `cancel` flag set (§36.2.3) | "Stopped by you after N tool calls." |
| Ceiling | cumulative tool calls across continuations ≥ `job_ceiling_tool_calls` | "Reached your job ceiling of N tool calls. Raise it in Settings → AI, or ask me to continue." |
| No progress | §36.1 timeout, unchanged | unchanged |
| Provider error | unchanged (`:12555`) | unchanged; billing errors never retry (INVARIANTS §4.3) |

### §36.2.2 Settings

> **Status: BUILT** (PR 3 + PR 8, #3050). The ceiling/checkpoint pair (`job_ceiling_tool_calls`/`max_tool_iterations`, including the `ceiling ≥ checkpoint` clamp both directions) landed in PR 3. **"Concurrent jobs" lands in PR 8**: a new Settings → AI row, same `handleAbBlur`-pattern shape, reading/writing `ai_settings.job_concurrency` — a key that already existed and was already read by `scheduler_tick` (`.unwrap_or(RUNTIME_DEFAULT_CONCURRENCY)`); only the UI row was new. No cross-field clamp (unlike the ceiling/checkpoint pair) — min 1 (a 0 would silently stall the entire scheduler).

- `ai_settings.job_ceiling_tool_calls` — new, integer, default **200**. Distinct from `max_tool_iterations`, which stays as-is. Shown in Settings → AI beside the per-turn limit, labelled "Overall job ceiling".
- Applies to **every** API-runtime turn, interactive or background. An interactive chat that needs 40 tool calls no longer stops at 30 and waits. (§36.14 #1 — decided yes, 2026-10-25.)
- **Relabel (Ruling 4, Matt 2026-10-27).** `max_tool_iterations` is a checkpoint interval, not a brake: every N tool calls the loop exits, writes the progress divider, re-runs the context-budget check (`maybe_compact_thread`, same function the pre-dispatch path already calls — required, not optional, so the reframing is real rather than cosmetic), and re-enters. Settings → AI shows both rows, relabelled:
  - **"Checkpoint every N tool calls"** — "the agent pauses to note progress and re-check context, then continues" — default **30** (same `ai_settings.max_tool_iterations` key/range as before, label text only changes).
  - **"Overall job ceiling"** — "hard stop per job; raise it here or ask the agent to continue" — default **200** (`ai_settings.job_ceiling_tool_calls`).
- **Enforce `ceiling ≥ checkpoint`: clamped, not validated/rejected.** Both backend read sites (`ai_chat_stream`, `scheduler::prepare_job_dispatch`) clamp the read `job_ceiling_tool_calls` up to `max_tool_iterations` via `.max(max_tool_iterations)`; Settings' own `handleAbBlur` applies the same clamp in both directions (raising the checkpoint above the current ceiling raises the ceiling to match, and the ceiling input's own `min` is the live checkpoint value) so the UI can never save an impossible pair even transiently. **Setting them equal reproduces today's (pre-PR-3) stop-at-N behaviour and is the documented escape hatch** for a user who wants the old "always ask before continuing" shape back.

### §36.2.3 Stop button and progress

- The chat input area shows **Stop** while a turn is running (interactive) or while a job bound to this chat is running (§36.4). Stop sets the per-session `cancel` flag; the loop checks it at the top of every iteration and before every continuation. A tool call already in flight completes; its result is saved; the loop then exits "Stopped".
- **(#3050 PR 6, Ruling 4) Stop must abort the in-flight provider stream, not only check the cancel flag between loop iterations.** The two checkpoints above are unreachable while a response is streaming — which, for an OC turn, is the entire turn. `stream_openrouter`/`stream_openrouter_inner` (also used by plain OpenRouter and Venice dispatch — a free win, not OC-specific) now take a `cancel: Arc<AtomicBool>` parameter and check it once per received SSE chunk, aborting the stream (`break`, dropping the still-unconsumed `reqwest` response body — how `reqwest` aborts an in-flight HTTP request, no separate `AbortHandle`) on a hit. Partial text is preserved via the SAME `(error, partial_text)` channel a mid-stream network error already used — reused unchanged, not a new mechanism; nothing async happens between "chunk appended to the running text" and this check, so no text is ever lost. `run_agent_loop`'s own `Err((e, stream_partial))` arm checks `cancel` BEFORE the OC-reconnect-retry branch (never by string-matching `e`) — a Stop must never reconnect a stream the user asked to end, and renders the "Stopped by you after N tool calls" copy, never the provider-error copy.
- **"In flight," ruled (Matt, 2026-10-27, #3050 PR 3 follow-up — fix(runtime): Stop drops an unstarted batch):** "in flight" means a tool call whose execution has started. A batch the model just returned is not in flight. Stop pressed before a batch starts drops the whole batch; nothing new dispatches. Only a tool already executing finishes, its result is saved, then exit Stopped. This replaces the prior first-call-of-a-batch exemption (which treated the batch's first call as already in flight merely because the provider round trip that produced it had already happened) — under this ruling, every call in a just-returned batch is checkable, including the first; a batch of 3 calls with Stop caught before dispatch executes 0 of them, and a batch where Stop is caught after the first call has already started executing (and is awaited) lets only that first call finish.
- Progress: the existing streaming surface shows text as it arrives. Continuations add a single line between turns: "Continuing — N tool calls so far." The transcript row is the `continued = 1` message from §36.2.1, so no new UI state is needed.
- **(#3050 PR 6) The composer gets a Send button that toggles to Stop in the same slot — no floating button.** The composer was Enter-only before this PR (zero buttons while idle, Stop popping in and out of an otherwise-empty composer while streaming — the live-test's "floating button" note). `ChatPanel.svelte`'s `.input-area` now renders ONE button in that slot, toggling on `isStreaming`: idle → "Send" (new; clicking it submits the composer's current text, parity with the pre-existing Enter-to-send keyboard path, which is unchanged); streaming → "Stop" (unchanged behavior from PR 3). Same position, same size, swapped label/icon/color.

### §36.2.4 Tests

- Ceiling: fake model that always returns a tool call; `max_tool_iterations = 5`, `job_ceiling_tool_calls = 12` → exactly 12 tool calls executed, 2 continuations, exit "Ceiling".
- Stop: set `cancel` after tool call 7 → exit "Stopped", 7 results saved, no further dispatch.
- Done: fake model returns tool calls for 2 iterations then text → exit "Done", no continuation message appended.
- OC-bound session with the same inputs → no continuation ever (gate test for §36.0.1).
- All through `run_agent_loop` with `MockRuntime` — the §36.1 extraction is what makes these possible.

### §36.3.1 What it is

One Pane-owned scheduler. Jobs are rows in `agent_jobs` (§36.10). A tick runs every 60 s while Pane is open and on launch, picks due rows, and runs them. There is no timer thread per job and no OS-level scheduling; the tick is the only clock — same restraint as §19.5's event-driven watcher.

### §36.3.2 Job kinds

| `kind` | Who creates it | When it runs |
|---|---|---|
| `once` | user (Schedules UI) or agent (`schedule_job`) | at `run_at` |
| `recurring` | same | per `cron` (5-field, local time), next computed on each completion |
| `heartbeat` | user, as a preset in the Scheduled panel | a `recurring` job created from the "Check in" preset, whose brief defaults to: "Review this project's open tasks and recent notes. If anything needs doing or deciding, do it or tell me. If nothing does, reply 'Nothing needed.' and stop." Not a per-agent setting; any agent can have one. |
| `reminder` | user or agent (`schedule_job(kind="reminder")`) | at `run_at` (always one-off — never `cron`, the inverse of `heartbeat`'s cron-only shape, #3120 PR 2 C4/C5). Fires with NO provider call: the brief is posted directly as the session's own reply. **Superseded (#3151 PR1):** the row above describing "the agent's one shared Reminders session, not a fresh session per firing" is the pre-#3151 behavior — see §36.3.6's own `fix(runtime)` note, below, for the retirement. A `reminder` job now gets its own fresh, job-titled session, the same as every other kind. |
| `spawn` | agent (`spawn_job`, §36.4) | immediately |
| `continuation` | never a row — §36.2 is in-loop, recorded here only to say so |

> **fix(runtime) (#3128, C23):** the `reminder` kind above (C4/C5, #3120 PR 2) was fully built and tested at the Rust level from the start, but `schedule_job`'s own tool schema never declared a `kind` property at all — a model calling the real tool had no way to discover `kind="reminder"` existed. Closed by adding `kind` (enum `["reminder"]`, optional) to the schema in the same commit; no backend behavior changed.

### §36.3.3 Running a job (API agent)

1. Tick selects rows `WHERE status = 'pending' AND next_run_at <= now ORDER BY next_run_at LIMIT <concurrency>`; sets `status = 'running'`, `started_at = now` in the same transaction (claim-before-run, so a second tick never double-runs).
2. Resolves the **job session**: the row's `session_id`, created at job creation (§36.3.6). The job session is bound to the job's `agent_id` — the normal `create_session(project_id, agent_id)` path (§30.2.1), so session binding stays immutable and attribution stays correct.

> **fix(runtime) (#3151 PR1, Commit G) — this invariant now has an enforced edit-time guard, not just a creation-time one.** `execute_update_job` (the Scheduled panel's Edit action, `ai/tools.rs`) wrote `agent_jobs.agent_id` from whatever the caller resolved, unconditionally, with no corresponding update to the job's own session's bound `agent_id` and no refusal on a changed value — editing a job and picking a different agent silently desynced the two, a real correctness bug Reed's scope audit found (§36.3.3 step 2's own words, quoted above, were already a given the code didn't actually hold). **Fixed:** the function now reads the job's existing `agent_id` first and refuses the whole call (writes nothing — not the brief, not the title, not the schedule, nothing) when the caller's resolved `agent_id` differs — "change agent = new job," not a silent rebind. The frontend half (`ScheduledPanel.svelte`'s Agent `<select>`, disabled during Edit with a "Change agent = new job" hint — Project stays editable) closes the UX gap the same ruling named; the backend guard is what makes the invariant actually hold even if a stale/bypassed frontend ever called this command directly.
3. Inserts the brief as a user message (`synthetic = 1`) and dispatches through `run_agent_loop` with `job_id` set, `continue_policy = auto`, and the ceiling from §36.2.2. The loop is the same loop; a job is a turn nobody typed. **Amended (#3120 PR 1, C17):** before dispatch, `prepare_job_dispatch` now also loads the real prior history of the job's origin session (or its own session for a job with no origin — always true for a wake row, §36.4.5) and runs the combined message set through the same `apply_budget` pass an interactive turn gets — see §36.4.5's own fix(runtime) entries for the full mechanism; this step is no longer `[brief_message]` alone.
4. On exit: `status = 'done' | 'failed' | 'stopped'`, `finished_at`, `last_error` (on failed), `tool_calls_used`. For `recurring`/`heartbeat`, `next_run_at` is recomputed and `status` returns to `pending`. **`'stopped'` wired PR 8, #3050, Matt's ruling:** nothing wrote this value before PR 8 — `JobOutcome` had only `Done`/`Failed`, so a job-bound turn the user stopped via the Stop button fell through to `'done'`, indistinguishable from a real success. `JobOutcome` gained a third variant (`Stopped`, checked before the provider-error flag, same priority Stop already has everywhere else in `run_agent_loop`); `write_job_terminal_status` (`ai/scheduler.rs`) is the one place the mapping happens.
5. §36.8 report-back runs, then §36.7 notification. **Amended (#3120 PR 1, C18):** when the report-back target (or, for a wake turn, the session it runs directly in) is the session currently open on screen, a live-refresh signal fires instead of/alongside the notification gate — see §36.7.1's own fix(runtime) entry and §36.8.1's "Live refresh" note for the exact mechanism. **Amended (C38, #3139):** the job's own-session write (`insert_wake_turn_reply`) now runs for every kind that reaches this step — `wake`/`recurring`/`heartbeat` as before, plus `once`/`spawn` — not only the three §36.4.5 already names; see §36.8.1's own fix(runtime) entry for why, and for the no-origin case this closes. **Amended (C40/C41/C42, #3147, live test #5):** report-back now covers **all kinds with an origin**, not just `spawn`/`once` — see §36.8.1's own fix(runtime) entry. All of this step's notification paths (a reminder's direct post, a recurring/heartbeat job's own-session write, report-back's own insert) key `emit_agent_message_notification` on the SAME per-firing identity: the `message_id` `insert_wake_turn_reply` mints (returned, not discarded, since this fix) via the existing `agent_message:{message_id}` convention — one key scheme, never a timestamp (every candidate column — `next_run_at`, the nonexistent `last_run_at`, the second-granular `started_at` — was checked and rejected; see §36.7's own fix(runtime) entry for the full reasoning). **Amended again (C42d, #3147, live test #5 FOLLOW-UPS, Matt's live-tested ruling):** a recurring/heartbeat job with an origin now ALSO notifies the origin (not just its own session) — Matt's walk watches the origin (Home), and the own-session bell alone was invisible there. Since this is the one case where BOTH the own-session write and the report-back write happen for the SAME firing (every other kind/origin combination gets exactly one of the two), reusing the bare per-firing identity for both would collide inside `emit_agent_message_notification`'s own dedup check (a plain `idem_key` lookup, global — not scoped by `target_id`/session the way `idx_chat_local_oc_dedup` is scoped by `thread_id`) and silently drop the second emit. The origin bell therefore suffixes the identity (`{message_id}-origin`) rather than reusing it verbatim — still derived from the same one per-firing UUID, still never a timestamp, just no longer byte-identical across the two notification targets when both fire.

**Concurrency:** 2 jobs at a time (`ai_settings.job_concurrency`, default 2, Settings → AI; Matt 2026-10-25). Interactive turns are not counted; they always run.

### §36.3.4 Running a job (OC agent)

> **C28(b) (#3129, Matt's ruling: "Pane is the toolset").** This section previously described a trigger-only `sessions.create`/`sessions.send` mechanism with its own `'sent'` resting status and its own transport-failure bookkeeping (`consecutive_failures`/`last_failed_at`). That mechanism is retired — see the retirement list in the #3129 PR body. A job whose agent is `openclaw` now dispatches through the exact same path every other runtime uses.

A job whose agent is `openclaw` dispatches identically to a job on any other runtime: `claim_due_jobs` claims it (unchanged — recurring/heartbeat `next_run_at` recompute at claim time is already runtime-generic, §36.3.5), `prepare_job_dispatch` resolves its `AiProvider::OpenClaw` config, and `run_agent_loop` runs the turn with the full Pane tool surface, writing into the job's own Pane session (`origin='spawn'|'schedule'`, §36.3.6) exactly as an interactive turn writes into a chat session. Terminal status (`done`/`failed`/`stopped`) is `write_job_terminal_status`'s job, the same function every other runtime's job turn uses — **there is no resting `sent` status for a newly-dispatched job.** OC `recurring`/`heartbeat` jobs recur on Pane's own clock exactly as before (§36.3.5, unaffected — that mechanism was already runtime-generic).

### §36.3.5 Missed jobs

On launch, and whenever the tick finds `next_run_at` more than one interval in the past:

- `once`: run now.
- `recurring` / `heartbeat`: run **once**, then recompute `next_run_at` from now. A schedule that missed 40 firings while the Mac was asleep runs one catch-up, not 40 (`missed_count` is incremented and shown in the UI).

## §36.4 Spawn (subagents)

> **Status: BUILT** (PR 5, #3050). `spawn_job` (`ai/tools.rs::execute_spawn_job`) lands with the **captain/crew** gate (§36.17 — `chat_sessions.crew_agent_ids`, replacing this section's old "any `ai_agents` row with `is_active = 1`" targeting rule). Depth (`RUNTIME_MAX_SPAWN_DEPTH = 2`, dispatch-time, the calling job's own `parent_job_id` presence — never a stored counter) and chain (`RUNTIME_MAX_CHAIN_DEPTH = 8`, offer-time, `agent_jobs.chain_depth`) are deliberately **two separate counters**, confirmed independent by a dedicated mutation pair (§36.4.4) — conflating them was the single biggest risk this PR's own scope audit named. `prepare_job_dispatch(true)` (the proactive-turn-tools branch PR 4 added but never exercised through a real dispatch) now runs end to end through a real `scheduler_tick` → `run_agent_loop` round trip in this PR's own tests, closing that residual gap.
>
> **fix(runtime) (Reed's 2026-10-28 audit, #3107):** the first shipped cut of this PR had both caps correctly IMPLEMENTED but UNREACHABLE on the one path that mattered — a woken turn re-calling `spawn_job`. `execute_spawn_job`/`execute_schedule_job` reset `chain_depth`/`root_job_id` to `0`/self on every call, discarding the calling turn's real chain position, so a spawn→wake→spawn→wake cycle never advanced `chain_depth` past 1 and `RUNTIME_MAX_CHAIN_DEPTH` never fired — proven live, 12 iterations, zero refusals. Both functions now carry the calling job's own `chain_depth`/`root_job_id` forward (§36.4.1), a fresh root ONLY for a genuinely interactive call. Matt's ruling, same follow-up: **self-spawn is refused outright** (§36.17.3) — a second, independent guard, not a substitute for the propagation fix (an A→B→A cycle loops identically without ever naming the same agent twice).

**Mode:** API-only.

### §36.4.1 Behaviour

`spawn_job(agent, brief, title?, wake?)` from a running API-runtime turn:

1. Creates an `agent_jobs` row, `kind = 'spawn'`, `origin_session_id` = the calling session, `agent_id` = the chosen agent — **a member of the calling session's own crew** (§36.17; refuses a non-member target with "not in this session's crew"), `project_id` = the calling session's surface. `origin_message_id` stays `NULL` — not resolvable from a tool call's own params today (no per-tool-call message id is threaded into dispatch context yet); stated as a known gap, not fabricated.
2. Creates the job session per §36.3.6, **inheriting the calling session's own crew verbatim** (§36.17) — the only workable answer, since otherwise a spawned session's own crew would default to NULL, `spawn_job` would never be offered inside it, and the depth-2 cap would be unreachable by construction.
3. Returns `job_id` to the calling model immediately with the tool result `"Spawned <agent> on '<title>'. You'll get the result in this chat when it's done."`. The calling turn continues; it does not wait.
4. The scheduler tick picks it up (`next_run_at = now`). The spawned turn runs with full tools under the same rules (§36.5) and the same project-write limit as its agent would have interactively — a project agent spawned from a project chat writes only there; a spawn from Home writes anywhere.
5. On completion, §36.8 posts the result into `origin_session_id`, and (§36.4.5) a wake turn fires unless `wake: false` was passed.

**OpenClaw agents as spawn targets:** `spawn_job` refuses `runtime_type = 'openclaw'` with the tool error `"spawn_job cannot target an OpenClaw-bound agent."` OC spawns originating in OC are read-side (§36.8).

**Depth:** a spawned job may itself call `spawn_job`; depth is capped at 2 (a spawn of a spawn is the floor — `RUNTIME_MAX_SPAWN_DEPTH`). Row carries `parent_job_id`. Checked at DISPATCH time only (`execute_single_tool`'s `spawn_job` arm), from the presence/absence of the parent_job_id on the CALLING job's own row — never a stored depth counter, and never conflated with the chain cap below (§36.4.5), which is a different axis entirely. **The CALLING row's own `kind` gates which signal this is** (fix(runtime), #3107): nesting only counts when `kind == 'spawn'` (a genuine spawn-of-a-spawn, same dispatch stack) AND `parent_job_id` is set; a `kind == 'wake'` calling row is always treated as depth-1-fresh for NESTING purposes regardless of its own `parent_job_id` (which now DOES carry a value — the finished job that triggered it, §36.4.5 — for provenance, not nesting). Without this `kind` guard, threading `parent_job_id` onto wake rows (the §36.4.5 fix) would make the depth-2 cap fire on the FIRST wake-mediated re-spawn of every cycle, making `RUNTIME_MAX_CHAIN_DEPTH` structurally unreachable — the opposite of the fix's intent.

**Chain position propagation** (fix(runtime), #3107): `execute_spawn_job`/`execute_schedule_job` carry the CALLING job's own `chain_depth`/`root_job_id` forward into the new row — a fresh root (`chain_depth = 0`, self-referencing `root_job_id`) ONLY when the calling turn has no job at all (a genuine interactive call, `ownJobId` absent from dispatch context). Before this fix, both functions reset `chain_depth`/`root_job_id` UNCONDITIONALLY on every call, so a woken turn (whose own row always looks depth-1-fresh for NESTING, by design) also looked chain-fresh on every hop — `chain_depth` never advanced past 1 and `RUNTIME_MAX_CHAIN_DEPTH` (§36.4.5) never fired, regardless of how many spawn→wake cycles ran. Reed's 2026-10-28 audit proved this live: 12 iterations of a self-crewed spawn→wake cycle, zero refusals, `chain_depth` stuck at 0 throughout.

**Self-spawn is refused** (Matt's ruling, §36.17.3): `spawn_job` refuses a target that IS the calling session's own bound agent, with the tool error `"spawn_job: <agent> is this session's own agent — an agent cannot spawn itself."` — a second, independent guard. An A→B→A cycle (two DIFFERENT agents, never naming the same one twice in a row) loops exactly the same way without ever tripping this check, so the chain-position propagation fix above is required regardless of this guard, not replaced by it.

### §36.4.2 Retention

Spawn sessions and their messages are archived after **30 days** (§36.14 #3) through the existing transcript-archive path (`[ARCHIVE]`, PR #690 lineage), not deleted. The `agent_jobs` row stays; its `session_id` continues to resolve to the archive.

### §36.4.3 Memory

Spawn-session transcripts are **not** fed to memory extraction (`origin = 'spawn'` is excluded at the queue; schedule sessions are extracted like any visible session, the same way §30.6 excludes by session state). The report-back message in the originating session is extracted normally — that is the part the user saw and the part worth remembering. (§36.14 #4.)

### §36.4.4 Tests

- Spawn from project chat → job session on the same project, bound to the target agent; `origin_session_id` set (`origin_message_id` asserted `NULL` — the documented gap above, not fabricated).
- Spawn targeting an OC agent → refused, no row.
- Depth 3 → refused.
- Spawned project agent calling `create_note` on another project → refused by the existing scope check (no new code; the test pins that the existing gate reaches spawned turns).
- Extraction queue skips a job-session message; accepts the report-back message (and the `origin='schedule'` message — not excluded, only `'spawn'` is).
- Spawn onto an agent not in the crew → refused (§36.17).
- No crew → `spawn_job` absent from the offered set (§36.17).
- **The depth-vs-crew distinguishing pair** (§36.17's own critical mutation): depth-blocks-but-crew-allows (target IS a crew member, calling turn is depth-2) and crew-blocks-but-depth-allows (calling turn is fresh depth-1, target is NOT a crew member) — each scenario's own mutation (deleting only that mechanism) reddens only its own scenario, proving the two checks are independent.
- **(fix(runtime), #3107) A job turn re-calls `spawn_job`, through the REAL dispatch cycle** (not a hand-seeded calling row): depth-1 spawn, direct same-turn re-spawn at depth-2 (allowed, the nesting floor), then a depth-3 attempt — refused, zero new rows.
- **(fix(runtime), #3107) A real spawn→wake→spawn→wake cycle, driven through `execute_spawn_job`/`create_wake_job`**, proves `chain_depth` climbs by exactly 1 on every wake hop (not pinned at 0/1 forever): starting from a fresh interactive spawn, the 8th wake created lands at `chain_depth = RUNTIME_MAX_CHAIN_DEPTH` (8) and that wake's own turn has `spawn_job` withheld — the chain ends there with a report; it cannot produce a 9th wake.
- **(fix(runtime), #3107) The shared ceiling across two REAL chain links**: a `spawn_job` call made from inside a wake turn produces a job whose `root_job_id` is the ORIGINAL chain root (not a fresh self-reference) — usage recorded against both links accumulates onto the one root row, not two independently-fresh budgets.
- **(Matt's ruling, §36.17.3) Self-spawn → refused, no row**: the calling session's own bound agent IS a crew member of itself (nothing upstream of this check refuses that configuration) — `spawn_job` targeting that same agent is refused at the tool, with a clear error naming self-spawn as the reason.

### §36.4.5 Wake-on-complete (chaining)

> **Status: BUILT** (PR 5, #3050). The wake row is an ordinary new `agent_jobs` row (`kind = 'wake'`, `ai::scheduler::create_wake_job`), claimed by the same `claim_due_jobs` path every other job uses — not a second dispatch path. `session_id = origin_session_id` (the turn runs directly in the real chat session); `origin_session_id` on the wake row itself is always `NULL`. The chain-shared ceiling is two real code changes: the post-completion bookkeeping write accumulates `tool_calls_used` onto the chain's root row instead of overwriting the finishing job's own row, and `prepare_job_dispatch`'s ceiling read subtracts the root's already-spent total before handing out `ceiling_remaining`. The OC-bound check reuses `resolve_runtime_config_for_session(...).runtime_type == "openclaw"` — the exact call `prepare_job_dispatch` already makes. The "archived" check is a stated proxy, not a literal flag: no `chat_sessions.archived_at`/`is_archived` column exists in this codebase; `last_active_at` older than `RUNTIME_JOB_ARCHIVE_DAYS` degrades a wake to report-only.
>
> **fix(runtime) (Reed's 2026-10-28 audit, #3107):** `create_wake_job`'s `parent_job_id` was hardcoded `NULL` on every wake row, unconditionally — now it's the id of the job that just finished and triggered this wake (provenance; §36.4.1 above explains why this does NOT make a wake row look nested for the DEPTH cap). `chain_depth`/`root_job_id` were already being computed correctly by this function at creation time (`finished_job.chain_depth + 1` / `finished_job.root_job_id`) — the gap was never here; it was `execute_spawn_job`/`execute_schedule_job` discarding those values the moment the NEXT job in the chain was created (§36.4.1).
>
> **fix(runtime) (#3120 PR 1, C17 — "wake turns load session history"):** `prepare_job_dispatch` built every job/wake turn from `&[brief_message]` alone, unconditionally — the exact mechanism behind live-test #2's quoted log line, `Iteration 1 with 2 messages`. Matt's ruling (issue #3120): "wake turns (and spawn-origin turns) load the last N messages of the origin session under the same context budget as an interactive turn." Both halves are mandatory together, never landed separately: `prepare_job_dispatch` now (1) fetches the dispatch target's real prior history — `job.origin_session_id` when the job has one (a spawn/once job's calling chat; a wake row's own `origin_session_id` column is always `NULL`, so this falls through to (2) below, which is the correct target for a wake anyway), else `job.session_id` — via `fetch_session_history_for_job_turn` (same `tools::CHAT_MESSAGE_BOOKKEEPING_COLUMNS` shape `maybe_compact_thread`/`load_chat_messages` already use, oldest→newest, synthetic/continued bookkeeping rows excluded), prepended ahead of the brief (which stays LAST, the position a freshly-typed user message occupies interactively); and (2) runs the resulting message set through `crate::ai::context_budget::apply_budget` — the identical pass `ai::chat::ai_chat_stream` already runs on every interactive turn, previously absent from this file entirely (zero call sites in `scheduler.rs`, six in `chat.rs`) and harmless only because the old `[brief_message]`-only array was never large enough to need it. Landing history without the budget pass would have been a regression the tiny pre-fix array never exposed — the two ship as one fix, not two.
>
> **fix(runtime) (#3120 PR 1, C22 — "one wake per sibling-completion batch"):** a captain fanning out N `spawn_job` children with the same `origin_session_id` produced N independent wake rows on N independent completions — confirmed, no dedup read before insert anywhere in the wake-creation block. Fixed with a SQLite partial unique index, `idx_agent_jobs_one_pending_wake_per_session ON agent_jobs(session_id) WHERE kind = 'wake' AND status = 'pending'` (plain index, no CRR rebuild-shape hazard — `agent_jobs` is explicitly non-CRR, §36.10), and an upsert in `create_wake_job`: the first sibling's completion creates the pending row; every subsequent sibling in the same pending-wake window updates it in place (briefs concatenated, not dropped — C17's history load means the woken turn sees every sibling's full report in session history regardless of which one's completion won the row). The slot frees itself the moment `claim_due_jobs` claims the row (`status` → `'running'`), so the next batch of completions creates a fresh pending wake rather than being blocked forever. **Not gated behind a `SCHEMA_VERSION` bump** — the index is created idempotently both at fresh-install time (`create_agent_jobs_table`) and, for every already-migrated install, unconditionally on every launch (`migrations::ensure_agent_jobs_wake_dedup_index`, called once after the version-dispatch `match` in `run_migrations_with_progress`), since `CREATE UNIQUE INDEX IF NOT EXISTS` on an existing table needs no DDL migration arm to reach pre-v96 installs that already have the table.
>
> **fix(runtime) (Reed's 2026-10-30 audit, #3122 FAIL #1; Matt's ruling: repair, then index):** `CREATE UNIQUE INDEX IF NOT EXISTS` only guards against the index already existing BY NAME — it does nothing for a session that already has more than one pending `wake` row at the moment the index is (re-)created, which fails the `CREATE` itself (`UNIQUE constraint failed: agent_jobs.session_id`). Once that happens — a startup failure via `run_migrations`'s `?`, not a degraded feature — `create_wake_job`'s own `ON CONFLICT(session_id) WHERE kind = 'wake' AND status = 'pending'` upsert has no matching partial index to target and hard-errors on EVERY wake creation, for every session, from then on. `ensure_agent_jobs_wake_dedup_index` now repairs before indexing: for every session with more than one pending wake, the OLDEST (by `created_at`) is kept and every other pending wake for that session is set to `status = 'cancelled'` — never deleted, so the sibling-completion history those rows carry is untouched — before the `CREATE UNIQUE INDEX` runs. `cancelled` rows can't conflict with the partial index afterward: the index's own `WHERE kind = 'wake' AND status = 'pending'` clause only matches `pending` rows, so a `cancelled` row is invisible to it by construction. This duplicate state is reachable even on a DB that has never seen a bug — the app quitting between two sibling completions and the next tick/relaunch is enough — so the repair runs unconditionally, every time this function runs, not only when upgrading from a pre-dedup install.

**Test (fixture, #3122 defect 1):** a session seeded with two pending wake rows (deliberately inserted newer-row-first, so the test cannot pass on insertion order alone) → `ensure_agent_jobs_wake_dedup_index` succeeds, exactly one pending wake survives (the older one by `created_at`), the other is `cancelled` (not deleted), the index exists afterward, and `create_wake_job` on that same session inserts/upserts cleanly immediately after. **Mutation:** remove the repair `UPDATE` → the test's `run_migrations` call fails with `UNIQUE constraint failed: agent_jobs.session_id`.

Report-back (§36.8) is an ingest and can never start a turn. On its own, that leaves the calling agent unaware a job finished — so "build, then audit, then tell me" cannot run without the user prompting each step. OpenClaw's coordinator pattern (Brit is woken when a spawn returns, decides the next step, tells the user) needs an equivalent.

**Mechanism:** every `spawn_job` and every chat-originated `once` job carries `wake_origin = 1` (default; `schedule_job`/`spawn_job` accept `wake: false`). When such a job exits, the **scheduler** — not the ingest path — enqueues a proactive turn (§36.5) on `origin_session_id`, bound to that session's agent, whose synthetic user message is: `"[Job '{title}' by {agent} finished: {status}]\n\n{report text}"`. The origin agent runs with full proactive tools: it can read the result, spawn the next job, write notes, and reply in the chat — which the user sees as "your agent telling you," exactly as with Brit on OC.

The root job's `job_ceiling_tool_calls` is shared across the chain (`tool_calls_used` accumulates on the root row). **This cap only BINDS now that `chain_depth` actually propagates** (§36.4.1, fix(runtime) #3107) — starting from a fresh interactive spawn (`chain_depth = 0`), the cap fires on the 8th wake created in the cycle (`chain_depth` reaches 8 there), ending the chain before a 9th wake can ever exist.
- A wake never fires into a session whose agent is `openclaw` (§36.0.1) or into a job session that has since been archived; it degrades to a plain report-back.
- The ingest invariant is untouched: `ingest_external_messages` still never dispatches. The scheduler is the single component permitted to start a turn nobody typed.

## §36.5 Proactive turns that act

> **Status: BUILT** (PR 4, #3050). `ToolPolicy { proactive: bool }` (`ai/chat.rs`, next to `TurnOrigin`; minimal now — `tainted`/`chain_depth` are §36.16's later-PR fields) is derived from `TurnOrigin` once per dispatch and applied at TWO independent points: offer-time (`ai::tools::get_pane_tools_for_runtime`'s new `proactive: bool` parameter, filtering the new `PROACTIVE_WITHHELD_TOOLS` const) and dispatch-time (`ai::chat::check_proactive_tool_policy`, a fourth gate inside `run_agent_loop`'s tool-call loop, same shape as `check_web_taint` — re-derives from `turn_origin` directly rather than consulting `offered_tool_names`, confirmed non-decorative by a dispatch-site-specific mutation, §36.5.4). Navigation no-op is one `NAV_TOOLS` wrapper placed before all three existing navigate-family branches, confirmed sufficient with zero handler changes.

**Mode:** API-only.

> **Ruling 2 note (Matt, 2026-10-27):** this section's "API-only" mode is about the *proactive turn itself* — OC never runs one in Pane; Pane never runs a loop for an OC agent, proactive or otherwise (§36.0.1). It is unaffected by Ruling 2's widening of the *schedule tool family's offer* to OC-bound sessions (§36.3.7): an OC-bound session can call `schedule_job` during its own normal, user-typed OC turn (handled entirely inside OC, outside Pane's dispatch), and the resulting job's eventual firing is still the OC-trigger-only send in §36.3.4, never a proactive turn this section's withheld-tool-set applies to.

A **proactive turn** is any turn the user did not type: scheduled, heartbeat, spawn, continuation. Today only user-typed turns exist for API agents, and OC's out-of-turn messages are message-only (Reed, #3036 §30.11 check). This section is the first time a turn nobody asked for can take an action, so it is stated mechanically.

### §36.5.1 Tool exposure

Proactive turns receive the session agent's normal tool set (§4.5, ADR-0064 web gate unchanged), **minus** the consent-gated set:

`PROACTIVE_WITHHELD_TOOLS = { delete_note, move_note, move_folder }`

These are the Rule 20 actions (delete / move / overwrite) that need the user's OK. Withholding is the mechanism: the tools are not in the offered set, and the dispatch gate refuses them if the model names one anyway. A proactive turn that needs one ends its turn by saying so in its report ("Needs your OK: delete 'Old draft'"), and the user does it, or asks for it, in a normal turn.

`edit_note` and `append_to_note` stay offered: edits are versioned (`maybe_save_manual_version`), so they are recoverable; the standing rule names delete/move/overwrite, and an edit is not an overwrite. (§36.14 #5.)

### §36.5.2 Web taint

Pane's taint protection (§4.6.3) covers every Pane-dispatched turn, proactive included, with no change: a proactive turn that fetches the web loses `MUTATE_EXISTING_TOOLS` for the rest of that turn exactly as an interactive one does — and since ADR-0064 Amendment 2026-11-09 that set includes `schedule_job`, `spawn_job`, `cancel_job`, `pause_job` and `resume_job`, so a tainted turn of any origin cannot create, alter or spawn a job; a job never starts tainted because no tainted turn can create one (Reed's #3106 C2). The guard is a property of `run_agent_loop`, not of `TurnOrigin`: any future origin that dispatches through the loop (Events, #3142) inherits it by construction and needs no line of its own; an origin that dispatched any other way would be a §36.11 violation first. **OC-dispatched turns are OC's.** Pane cannot gate tool calls it does not dispatch; #3050's "coverage across both paths" is answered by stating that boundary, not by reaching into OC.

### §36.5.3 Navigation tools

`navigate*`, `show_view`, `set_filter` are UI-driving tools. In a proactive turn they are **offered but no-op** (return `"Not available in a background job."`), so a scheduled job never yanks the user's screen. Offered-not-withheld because the model's instructions reference them and a tool error is clearer than a missing tool.

### §36.5.4 Tests

- Proactive turn: offered set lacks the three withheld tools; a model that names `delete_note` gets the gate refusal, nothing deleted.
- Interactive turn, same session: offered set includes them (no regression).
- Proactive + web fetch: `MUTATE_EXISTING_TOOLS` withheld after the first external result (existing test extended with `job_id` set).
- `navigate_home` in a proactive turn → no-op result, no `navigate` action emitted.

### §36.7.1 `pane-chip-changed` — live chip refresh, a second and deliberately separate event

> **Status: BUILT** (PR 6, #3050).

**Decision: a new, narrowly-scoped event, not an extension of `pane-data-changed`.** `pane-data-changed`'s `entity_type` is a closed five-value enum (§34.1, `refresh_event.rs`) and `reason` a closed four-value enum — both pinned by existing tests, including one (`ai/tools.rs`) that exists specifically because the schedule/job family does NOT fit that enum. A chat-message chip is append-only (no "move," no UI-level "delete") and its status values (`sent`/`done`/`failed`) are job states, not edit-lifecycle reasons — forcing either axis would either need a sixth `entity_type`/new `reason` value (risking every one of `pane-data-changed`'s existing listeners across `notes.rs`/`projects.rs`/`scheduler.rs`/`ai/tools.rs`/multiple `src/lib` stores) or throw away the one piece of information `reason` exists to carry. **Two mechanisms, correctly, not one and not three:** `pane-notification` (persisted, dismissible, cross-session, OS-popup-capable — for a session the user is NOT looking at) and `pane-chip-changed` (ephemeral, unpersisted, same-session-only — for a session the user IS looking at) solve genuinely different problems.

**Event:** `pane-chip-changed`, payload `{ job_id: string, session_id: string, status: "inserted" | "done" | "failed" }`. **(`"sent"` retired, #3129/C28(b) — see §36.3.4; no job settles at a resting `'sent'` status anymore, so nothing emits it.)**

**Emit sites**, all in `ai::scheduler`:
- **Insert** — inside `insert_schedule_confirmation_message` (the one function both `schedule_job` and `spawn_job` write their chip through, §36.3.6/§36.4), right after the `INSERT` succeeds. Covers both chip kinds for free — one call site, not two kept in sync by hand.
- **Status flip** — `write_job_terminal_status`'s terminal write (`done`/`failed`) for every runtime's job turn, `openclaw` included (§36.3.4, #3129). **Deliberately NOT emitted at the `'running'` claim write** — Ruling 3 (Matt, 2026-10-29) names the chip's own status values explicitly; the chip's existing 5s poll already covers the transient `running` state adequately.

`ChatPanel.svelte` adds one `listen('pane-chip-changed', ...)` scoped to `payload.session_id === currentThreadId`: `status === "inserted"` triggers a full `loadMessages()` re-fetch (a new row exists); any other status updates `jobStatuses[payload.job_id]` directly. Each sub-case's mutation (drop that specific emit call) reddens only that sub-case, proving the mutation is scoped to the right call site.

## §36.8 Report-back

> **Status: BUILT** (PR 5, #3050). Written from `ai::scheduler::scheduler_tick`'s post-`run_agent_loop` hook via `ai::ingest::ingest_external_messages_impl` (now `pub(crate)` for this exact caller). `run_agent_loop`'s own return type grew from a bare tool-call count (`u32`) to `AgentLoopResult { tool_calls_used, final_text, outcome: JobOutcome }` — a real, audited signature change across all 11 call sites in `ai/chat.rs` — so the scheduler has real final text and a coarse done/failed signal to report back with.

### §36.8.1 Pane jobs (API-only)

On a job exit, Pane writes **one assistant message** into `origin_session_id` — for every kind that has one, since C42 (#3147, below): `spawn`, chat-created `once`, and (as of C42) `recurring`/`heartbeat`. `recurring`/`heartbeat` jobs ALSO write to their own schedule session (§36.3.6, C38/#3123 below) regardless of whether an origin exists — unlike `spawn`/`once`, whose own-session write only happens when there is NO origin (C38's "never two" rule). A notification (§36.7) fires if the relevant session isn't the open one:

> **fix(runtime) (C42, #3147, live test #5, Matt's ruling) — report-back widened to recurring/heartbeat.** The paragraph above previously restricted report-back to `spawn`/chat-created `once` — Matt's ruling: recurring/heartbeat jobs with an origin get the SAME report-back copy into the origin chat that once/spawn get, a plain insert, no wake. **A hidden third fix, beyond the issue's own text (Reed's audit §3):** widening the `kind` gate alone is not sufficient — `ExternalMessage::source_message_id` (stored as `chat_messages_local.oc_message_id`, under `idx_chat_local_oc_dedup`'s UNIQUE INDEX on `(thread_id, oc_message_id)`, `migrations.rs`) was job-id-only (`job-report-{job_id}`), safe only because `once`/`spawn` fire at most once ever. Fixed by reusing the SAME per-firing `message_id` C40/C41 key on (§36.7's one key scheme): the report-back key is the id `insert_wake_turn_reply` minted for this firing's own-session write, falling back to the job-id-only form only if that insert itself failed. **C39's wake-on-complete guard (§36.4.5) is unchanged** — confirmed a structurally separate `if` statement (report-back only ever calls `ingest_external_messages_impl`, a plain INSERT; wake-on-complete only ever calls `create_wake_job`, a new `agent_jobs` row; no shared boolean, no fallthrough between the two), with a standing regression test (`test_recurring_job_with_origin_still_creates_no_wake_job_after_c42`) locking it. **Tests:** `test_recurring_job_with_origin_gets_report_back_copy_c42` (mutation: revert the kind-widen — reddens, zero rows in origin); `test_recurring_job_second_firing_report_back_produces_second_row_c42b` (mutation: revert the key fix alone, kind-widen left in place — reddens, second firing dedup-skips to one row); `test_recurring_job_with_origin_still_creates_no_wake_job_after_c42` (mutation: drop the kind clause from the wake-on-complete gate — reddens, a wake row appears).

> **fix(runtime) (#3120 PR 2, C16):** this section previously documented only `read_attachment`'s own behavior once called — it said nothing about the vision-enrichment loop (`ai/chat.rs`, inside `ai_chat_stream`) that decides whether the model learns an attachment exists at all BEFORE it can call this tool. The image-deferral line and the unsupported-type message are both Pane-authored strings and do NOT taint (same "Pane-authored error strings do not taint" rule §4.6.3 already states for `web_fetch`'s own error surface). `read_attachment`'s "Tools used" line shows `read_attachment(<filename>)`, never the content, success or failure alike. The tool is in the web-tool allowlist's sibling: offered to API runtimes only (§36.0.1 — OC agents have their own file access).

**Taint mechanism renamed for honesty (§4.6.3):** `web_tainted`/`check_web_taint` → `external_content_tainted`/`check_external_content_taint` — the mechanism was already generic over the bool and tool name (one flag serves both `web_fetch`/`web_search` and `read_attachment`), but the OLD name specifically said "web," which became inaccurate once a local file read also trips it. ## §36.17 Captain/crew

> **Status: BUILT** (PR 5, #3050). **"Captain/crew" is the product name** (Matt's ruling) for the mechanism that replaces §36.4.1's old "any active Pane agent" `spawn_job` targeting rule.

**A session has a crew: the set of agents its captain may spawn onto.** Default is no crew, and no crew means `spawn_job` is not offered at all — a strictly opt-in capability, never "every agent can recruit every other agent" by default. **Crew is API agents minus the captain** (Matt's ruling, §36.17.3) — a captain is never its own crew, even if `crew_agent_ids` happens to list it.

### §36.17.1 Mechanism

- `chat_sessions.crew_agent_ids` — a nullable `TEXT` column, JSON array of `ai_agents.id`. `NULL` (or an empty array) = no crew. Added by migration **v93 → v94** (`migrate_v94`) — the only new DDL this PR adds; every other PR-5 column (`parent_job_id`, `root_job_id`, `chain_depth`, `wake_origin`, `origin_message_id`) already existed on `agent_jobs` since PR 2's v93 migration and is simply threaded through `create_job`'s own `NewJobParams`/`INSERT` for the first time here.
- **Two independent checks, not one:**
  1. **Offer-time** — "does this session have a crew AT ALL." `ai::tools::get_pane_tools_for_runtime` gains a `has_crew: bool` parameter (alongside PR 4's `proactive`); both production call sites (`ai_chat_stream`, `ai::scheduler::prepare_job_dispatch`) resolve it via `ai::tools::session_has_crew`, keyed on the turn's own running session. `has_crew = false` removes `spawn_job` from the offered set.
  2. **Dispatch-time** — two sub-checks inside `execute_spawn_job` itself, independent of the offer-time filter (so a future offer-time bug is not the only thing standing between a no-crew session and `spawn_job`): (a) re-derives "does the calling session have a crew" directly from `crew_agent_ids`, refusing if empty/absent; (b) "is THIS specific target agent a crew member" — a per-call-argument question the offer-time check cannot answer, since the model hasn't named a target yet when tools are offered.
- **Inheritance.** A spawned session (`origin = 'spawn'`) inherits its captain's crew **verbatim**, read from the calling session (`origin_session_id`) at creation time, inside `create_job`. Schedule sessions (`origin = 'schedule'`) never inherit — a schedule session is single-agent recurring execution, not delegation, so it always gets `NULL` regardless of the calling session's own crew. This is the only choice that makes a depth-2 spawn chain reachable at all: without inheritance, a spawned session's own crew would default to `NULL`, `spawn_job` would never be offered inside it, and §36.4.1's own "depth is capped at 2" line would describe a state the crew gate never lets the code reach.
- **Picker UI: BUILT, PR 10** (§36.17.4 below) — superseding this bullet's earlier claim that a dev-only Tauri command exists for this. Reed's PR 10 scope audit grepped every `generate_handler!` registration and every `dev_*` function in `src-tauri/src/` and found zero matches containing "crew" — that command never existed; PR 5's own live test almost certainly used a direct SQL write or the test-only `seed_session_with_crew` helper (`ai/tools.rs`, `#[cfg(test)]`-gated, never a Tauri command). Fixed forward here rather than left to mislead the next reader, same discipline as §36.11/Ruling 1 and Ruling 5 (notifications, PR 6).

> **fix(runtime) (#3120 PR 3, C13, Matt's ruling):** dispatch-time target resolution in `execute_spawn_job` gains one more step before falling through to "Agent not found" — a case-insensitive PREFIX match against the CALLING SESSION's OWN crew only (never the global agent roster, since a captain names a crew member it already knows about, not any agent in the install): exactly one match resolves silently ("Valencia" → "Valencia Tool Test"), zero falls through unchanged, more than one refuses, naming every candidate so the caller can retry with the full name.

### §36.17.2 Depth vs. chain — two separate counters, never conflated

Both the depth cap (§36.4.1, `RUNTIME_MAX_SPAWN_DEPTH = 2`) and the chain cap (§36.4.5, `RUNTIME_MAX_CHAIN_DEPTH = 8`) can refuse a `spawn_job`/`schedule_job` call, but they answer two different questions on two different counters:

- **`parent_job_id` presence** (no new column) — concurrent nesting WITHIN one turn-chain: a spawn calling a spawn, same moment. Dispatch-time only.
- **`chain_depth`** (existing column, newly populated) — sequential wake-chaining OVER TIME: a job finishes, wakes its origin, the origin spawns the next one, repeat. Offer-time only, via `get_pane_tools_for_runtime`'s `chain_capped: bool` parameter.

A depth-1 spawn can be wake-chained 8 times; a depth-2 nested spawn's own wake, when it fires, still only increments `chain_depth`, never `parent_job_id` — the two numbers move independently. This was the single biggest risk Reed's scope audit named for this PR; §36.4.4's "depth-vs-crew distinguishing pair" test and this section's own dedicated chain-vs-depth tests (`ai::scheduler::scheduler_v2_tests::test_chain_capped_withholds_spawn_and_schedule_job`, `test_wake_row_propagates_chain_depth_and_root`) pin the distinction directly.

**fix(runtime) (Reed's 2026-10-28 audit, #3107):** the first cut of this PR got the two-counters SHAPE right but the PROPAGATION wrong — see §36.4.1 for the full account. Two corrections, both load-bearing for this section's own claims: (1) `chain_depth`/`root_job_id` must be CARRIED FORWARD by `execute_spawn_job`/`execute_schedule_job` on every job-turn call, not reset — otherwise "a depth-1 spawn can be wake-chained 8 times" (above) describes a state the pre-fix code could never reach (12 live iterations, zero refusals, `chain_depth` stuck at 0). (2) once `create_wake_job` also threads `parent_job_id` (provenance — which job finished and triggered the wake), the depth cap's own "`parent_job_id` presence" signal must be scoped to `kind == 'spawn'` calling rows only — a `kind == 'wake'` calling row's `parent_job_id` is now always non-`NULL` too, and counting that as nesting would make `RUNTIME_MAX_SPAWN_DEPTH` (2) fire on the FIRST wake-mediated re-spawn of every cycle, making `RUNTIME_MAX_CHAIN_DEPTH` (8) structurally unreachable — exactly backwards from this section's own "a depth-1 spawn can be wake-chained 8 times" guarantee.

### §36.17.3 Self-spawn is refused (Matt's ruling)

**Crew is API agents minus the captain** — so `spawn_job` refuses a target that IS the calling session's own bound agent, at the tool, with the clear error `"spawn_job: <agent> is this session's own agent — an agent cannot spawn itself."`, regardless of whether `crew_agent_ids` happens to list that agent (nothing upstream of this check refused that configuration — a captain naming itself in its own crew was always possible, §36.17.1 never validated against it).

**This is a second guard, not THE fix.** An A→B→A cycle (two distinct agents, the calling session's own bound agent never repeating in consecutive hops) loops exactly the same way without ever tripping this check — it is the §36.4.1 chain-position propagation fix that actually bounds that case. Shipping the self-spawn refusal alone, without the propagation fix, would have left the headline exploit from Reed's audit (a session whose crew is `["captain"]`, i.e. itself) blocked, while the equally-real A→B→A shape remained wide open.

### §36.17.4 Picker UI (PR 10, #3050) — status: BUILT

## §36.18 Job-turn project identity and the write guard

> **Status: BUILT** (#3167). Closes the hole #3166/C54's own audit surfaced: the cross-project write guard (§4A.5) and the Home-only guard were never entered for a job turn at all, regardless of which project the job belonged to.

### The hole

`tools.rs::execute_single_tool` derived `session_project_id` from `context.get("projectId")` alone. A job turn's `context_clone` (built once, at `scheduler.rs::scheduler_tick`, for every job kind) never sets `"projectId"` — deliberately, per #3050 PR 4's own doc comment (preserved verbatim, see below) — so `session_project_id` was `None` for EVERY job turn, and both guards that branch on `if let Some(session_pid) = session_project_id`/`session_project_id.is_some()` were simply never entered. Reed's audit (issue #3167) found this closed 22 live holes in one pass: 21 of the 24 `ToolAccess::Write`-marked tools reachable from a job turn (`edit_note`, `set_sheet_cells`, `schedule_job`'s optional `project_id` arg, `cancel_job`/`pause_job`/`resume_job`, `generate_image`, and 16 more — only `delete_note`/`move_note`/`move_folder` are withheld from job turns regardless, by `PROACTIVE_WITHHELD_TOOLS`), plus `create_project` (`ToolAccess::HomeOnlyWrite`). A Content-project job could write into Aurum with zero refusal.

### Matt's ruling — parity, not new policy

Three options were on the table; Matt chose the first, explicitly rejecting the other two:

1. **(Chosen) Thread the job's own project into the guard as a distinct input**, so a job turn is authorized exactly as the same request typed interactively in the job's own project's chat would be. A job created in Content writes in Content. A job created in Home keeps Home's existing cross-project allowance, unchanged — exactly as if the same ask had been typed in that chat.
2. **(Rejected) Leave it** — "that's the hole with a label on it."
3. **(Rejected) Make every job turn stricter than Home**, regardless of the job's own project — this would make a Home job WEAKER than a Home chat, and the content machine would hit that the first time a Home job writes into a project.

**Target is parity, not new policy.** Nothing about WHICH tools are checked, or what the guard functions themselves do, changes — `check_cross_project_write_permission` and `check_home_only_tool_permission` are byte-unchanged by this fix (save the one pre-existing ad hoc normalization callout below). Only what `execute_single_tool` — and the one call site that bypasses it, `generate_image`'s dispatch branch in `chat.rs` — passes to them as `session_project_id` changes.

### The mechanism

A SECOND, job-only `context_clone` key, `"jobProjectId"` (`String`, = `ClaimedJob.project_id`/`agent_jobs.project_id` verbatim — the literal Home sentinel `"workspace"` for a Home-originated job, or a real `projects.id` otherwise), added at `scheduler_tick`'s one `context_clone` construction site (`build_job_context_clone`), alongside the pre-existing `"sessionId"`/`"dispatchAgentId"`/`"ownJobId"`/`"parentJobId"`.

**`"projectId"`'s existing exclusion stays intact, unconditionally.** #3050 PR 4's reasoning for never setting `"projectId"` on a job turn's context — so every OTHER reader of `context.get("projectId")` (`execute_spawn_job`'s target default, `show_view`'s resolved project, `execute_read_attachment`'s scoping) stays byte-identical the moment a job carries a project — still holds, and this fix does not touch it. `"jobProjectId"` is read ONLY by the two guard-side derivations below; no other function in the codebase reads this key.

**The two guard-side readers**, each independently applying the identical fallback (not a shared function between the two, since they live in different modules with different local variable shapes — see §4A.5 for the "is this the hole's shared predicate" distinction, which is about the Home-sentinel check, not this fallback itself):

1. `tools.rs::execute_single_tool`'s `session_project_id` derivation: read `"projectId"` first (unchanged); if absent, fall back to `"jobProjectId"`, mapping the literal Home sentinel (`"workspace"`/empty string) to `None`.
2. `chat.rs`'s `generate_image` dispatch branch's own copy of the same derivation (this branch bypasses `execute_single_tool` entirely — its own async dispatch, needed because the OpenRouter/Venice call requires `.await` — so it calls `check_cross_project_write_permission` itself, explicitly, and needs its own copy of the fallback).

**The landmine, named explicitly:** the "workspace" → `None` translation is NOT optional. Home's cross-project allowance IS the absence of a check — feeding the literal `Some("workspace")` into the guard instead would make `resolve_project_id` fail to match any real project, fall back to the raw string `"workspace"`, and then refuse EVERY write a Home job makes, anywhere — a Home job strictly WEAKER than a Home chat, the exact regression option 3 above was rejected for. Named, dedicated tests at both guard-side readers prove this does not happen (`tools.rs::job_turn_guard_tests_3167::test_job_turn_home_project_writes_to_any_project_note`, `chat.rs::job_turn_image_guard_tests_3167::test_job_turn_generate_image_home_project_writes_to_any_project_note`).

### Spawn and wake turns — covered automatically

`chat.rs::TurnOrigin` has exactly two variants, `User` and `Job` — every job kind (`once`, `recurring`, `heartbeat`, `spawn`, `wake`) dispatches through the SAME `scheduler_tick`/`TurnOrigin::Job` path this fix touches. A spawned job's `ClaimedJob.project_id` is the `target_project_id` `execute_spawn_job` resolved at spawn time; a wake job's is read fresh from the origin session's `chat_sessions.project_id` at `create_wake_job` time. Neither kind has (or has ever had) a separate dispatch path, so both inherit this fix with zero kind-specific code — a fact worth stating explicitly so a future reader doesn't go looking for a wake-specific branch that was never needed.

### A pre-existing ad hoc normalization, folded in

#3168's delta re-audit found a THIRD raw, unnormalized read of `agent_jobs.project_id` — `tools.rs`'s `cancel_job`/`pause_job`/`resume_job` guard arm, inside `check_cross_project_write_permission` itself — alongside `image_gen.rs`'s C54 tier-2 check and `memory_router.rs::determine_destination`'s pre-existing one, naming the risk that #3167's own new fallback would become a FOURTH independent copy of the same "is this the Home sentinel" comparison. Folded all four onto one shared predicate (`tools.rs::normalize_home_sentinel`) rather than writing a fourth — this is the only place `check_cross_project_write_permission`'s own body changes for this fix; every other guard-arm in that function is untouched.

### Cross-reference

See §4A.5 ("Tool Read/Write Marking & the Project-Scoped Write Guard") for the guard's own full mechanism and the job-turn case added there, and §36.3.7's existing "`schedule_job` respects the access rule… same rule as writes" sentence — this fix is what makes that sentence actually true for every job-turn write tool, not just `schedule_job`, rather than aspirational.

## §39.0 Purpose

Agents can make an image and put it where the brief says. First user: the content machine (Big Brain adds a header to each article note; social posts get an image under each). Out of scope: editing an existing image, reading images (that's the vision flag, roadmap 2.4), video.

## §39.1 Providers

One capability, two adapters. Each is a plain HTTPS call to a provider the user already has in **Provider Connections**; no new key is ever entered. **C50 (#3171 PR 1) is now resolved**: before C50 the AI tab asked for the OpenRouter key three times (Provider Connections, Smart Features, Semantic Search) and image generation was deliberately built to the Provider-Connections-only shape rather than adding a fourth; C50 made Smart Features and Semantic Search read Provider Connections too, so this section's "no new key is ever entered" guarantee now holds for every AI feature, not just this one.

| Provider | Endpoint | Returns | Model list |
|---|---|---|---|
| OpenRouter | `POST /api/v1/images` — `{model, prompt, aspect_ratio?, resolution?, quality?}` | `data[].b64_json` + `media_type`; `usage.cost` when present | `GET /api/v1/images/models` |
| Venice | `POST /api/v1/image/generate` — `{model, prompt}` plus the size parameters that model accepts — the adapter branches per model from the model-list metadata (Reed, 2026-11-03; confirmed against Venice's live docs at build time, #3161 PR 2: genuinely **three** shapes, not two — pixel-only (`width`/`height`), aspect-ratio-only (`aspect_ratio`, rejects `width`/`height` with a 400), and aspect-ratio-with-resolution-tier (both `aspect_ratio` and `resolution`), told apart by `constraints.aspectRatios`/`constraints.resolutions` presence on `GET /models?type=image`). Response is `{images: [base64, ...], ...}`, with **no cost/usage field of any kind** — confirmed against the live schema, not assumed — so `cost` is always omitted for Venice, same as OpenRouter's unreported case. | base64 image(s) | Venice `/models` filtered to image type |

Anthropic has no image output and is not listed. **Ollama is not a provider here** (Matt, 2026-11-03): its image generation is CLI-only with no HTTP API, so there is nothing to call. A generic "OpenAI-compatible local image endpoint" connection (Automatic1111, ComfyUI and similar expose one) is the right shape for local generation later — after launch, not this sprint. OpenClaw agents get `generate_image` like any other Pane tool (C28(b)): the call goes through Pane's adapter with Pane's provider connection, never through OC. Endpoints verified by Reed against current docs (review 2026-11-03).

**Build order (roadmap 3.2):** OpenRouter first, Venice second.

## §39.2 Settings → AI → Image generation

A new section on the AI tab, shaped like Semantic search but with **no key field**:

- **Provider** — dropdown of connected providers that offer image models (empty state: "Connect OpenRouter or Venice to generate images").
- **Image model** — dropdown populated from the chosen provider's image-model list (§39.1), with the per-image price shown where the provider reports it; nothing shown where it doesn't.
- **Test** — generates one small image from a fixed prompt into Home/Assets and shows it inline, same pattern as Web search's Test.

The first two are null until the user picks; `generate_image` returns a clear error ("No image model chosen — Settings → AI → Image generation") when unset. No default is chosen on the user's behalf.

## §39.3 The tool

```
generate_image
  prompt       string   required
  note_id      string   optional — embed into this note
  position     string   optional — "top" | "bottom" | "after:<exact heading or line text>"; default "bottom" when note_id is given
  alt          string   optional — alt text; defaults to the first 80 chars of the prompt
  aspect_ratio string   optional — "1:1" | "16:9" | "4:3" | "3:4" | "9:16"; passed through where the provider accepts it natively, translated to pixel width/height by the Venice adapter for pixel-only models (#3161 PR 2, §39.1)
```

Behaviour:
1. Resolve provider + model from settings (§39.2). Unset → error, no call.
2. Call the adapter. Timeout 120 s. One retry on a 5xx; none on 4xx.
3. Decode to bytes; write `Projects/<project>/Assets/<uuid>.<ext>` (Home: `Home/Assets/`) through the existing attachments path (`attachments.rs`), which also inserts the `attachments` row (`mime_type` from `media_type`, `size_bytes`, `original_filename = <uuid>.<ext>`). The destination project is resolved by a 4-tier priority, checked in this order (#3166 C54): **(1)** `note_id` given → the **note's own project** (`SELECT project_id FROM notes`), so the file always lands beside the note it's embedded into, regardless of which project the turn itself is scoped to. **(2)** No `note_id`, but this is a job turn (its context carries `ownJobId`) → the **job's own project** (`SELECT project_id FROM agent_jobs`) — a job turn's `context` deliberately omits `projectId` (#3050 PR 4), so without this tier a job's standalone (no-`note_id`) image would fall through to tier 4. **Correction (Reed's audit, 2026-11-04):** `agent_jobs.project_id` for a Home job is the literal string `"workspace"` (`create_session_internal`'s own Home surface id, `scheduler.rs`) — a DIFFERENT sentinel than this tool's own Home sentinel (`"__global__"`). Tier 2's lookup normalizes `"workspace"` (and empty) to "unresolved" before handing off to tier 4, the same normalization `memory_router.rs::determine_destination` already applies for the identical reason ("'workspace' is not a real project ID") — without it, a Home job's standalone image landed in a bogus `project_id = "workspace"` legacy attachment leaf instead of `Home/Assets/`. **(3)** No `note_id`, interactive turn → the **turn's project** (`context`'s `projectId`). **(4)** None of the above resolved → Home. The cross-project write guard (below) already forces the note's project to equal the turn's project for every interactive project-scoped call that reaches this step, so tier 1 outranking tier 3 is a no-op there; it only changes behaviour for Home-turn-into-a-project-note and job-turn calls, which is the point of the fix.
4. If `note_id` is given: insert exactly what the editor writes for a fresh image — plain markdown `![<alt>](Assets/<uuid>.<ext>)` on its own line (the `<div data-attachment …>` block is only what a *resized* image serializes to; Reed, 2026-11-03) — at `position`, via the existing note-write path so the editor round-trips it. `after:<text>` matches the first occurrence and the result says which; no match → `bottom` and the result says so.
5. Tool result: `{attachment_id, path, width, height, cost?}` — ids and a path, never image bytes, so nothing re-enters model context. **`path` is the project-agnostic relative form `Assets/<attachment_id>.<ext>` (#3178) — never the absolute disk path `attachments.rs::save_attachment_bytes` resolves internally.** The absolute path contains the real user's home directory; handing it to the model let it echo straight into a chat reply, and from there into persisted message content and any notification built from that reply's first line — a data leak, not just a display concern. `attachment_id` alone is already sufficient for the frontend's thumbnail rendering (`load_chat_messages` SELECTs `attachment_ids` unconditionally — #3171 PR2); the model never needs a filesystem-resolvable path, only one that avoids awkward prose without exposing the real layout. `cost` is present only when the provider reports it; a missing cost is omitted, never printed as 0. Chat rendering of the result is §39.5.

   **Defense-in-depth and repair (#3178):** `notifications.rs::emit_agent_message_notification` runs every notification body (built from an agent reply's first line) through `image_gen.rs::relativize_absolute_asset_paths` before persisting — the same rewrite the forward fix above makes unnecessary going forward, kept as a boundary guard against historical content and future regressions alike. A one-time, idempotent, flag-gated migration (`migrations.rs::repair_absolute_image_paths_once`, same shape as #3163's orphaned-embed repair) rewrites any already-persisted `chat_messages_local.content` row containing an absolute `Assets/<uuid>.<ext>` reference to the relative form — no schema bump; content-only.

The brief decides placement. "Header image" → the agent passes `position: "top"`. "An image under each post" → the agent calls once per post with `after:<post heading>`. The tool never guesses.

## §39.4 Gates

- **Proactive turns (§36.5):** `generate_image` spends money. It is **offered** on job turns (the content machine is a job) but counted: a job turn may call it at most `max_images_per_turn` (setting, default 4, stored as a third `ai_settings` key alongside `image_provider`/`image_model` — no migration, #3161 PR 2). Over the cap → tool error, turn continues. Interactive turns are uncapped.
- **Counter placement:** the per-turn image count lives on the turn's own state and dies with the turn — not in a session-keyed map (#3122's budget map was never evicted; don't repeat it).
- **Cost line:** every call logs `[IMAGE] provider=… model=… cost=…` (cost omitted when unreported) and the job session's receipt includes the image count and total cost when known.
- **Duration:** a 120 s call × one retry × four images is long but not a hang — the no-progress timer resets per completed call. The chat shows the tool-call-in-progress state as it does for any slow tool; no new UI.
- **Untrusted content (§4.6):** the prompt is model-authored from the brief; nothing from the generated image re-enters the model (no vision in this sprint).
- **Smart routing:** a turn that calls `generate_image` is tool-requiring. This needs no manual edit to `non_tool_name_bypass_patterns()` (C34) — `tool_bypass_patterns()` (chat.rs) auto-derives from the tool registry the moment `generate_image` is registered (its name splits to tokens `["generate", "image"]`, both ≥3 chars), and `non_tool_name_bypass_patterns()`'s own contract is to hold only tokens that are *not* tool-name-derivable. Adding "image" there would contradict that contract, not fulfil it.
- **Cross-project write guard (§4A.5, `check_cross_project_write_permission`):** `generate_image` carries an optional `note_id`, the same resource-pointer shape as `edit_note`/`append_to_note`. It gets its own arm in that function's match (conditioned on `note_id` being present, since unlike its siblings the param is optional): a project-scoped agent cannot point `note_id` at another project's note. Without this arm a write tool with an unlisted name falls to that match's `_ => Ok(())` default and is silently permitted — the refusal must land before the provider is ever called, since the call spends real money (Matt, 2026-11-03). **This arm is offered on job turns** ("the content machine is a job," above) — and until #3167, being offered was the whole gap: a job turn's `context` never carried `projectId`, so this arm (and all 21 of its `ToolAccess::Write` siblings) was NEVER ENTERED for a job turn, regardless of which project the job belonged to. §36.18 closes this: job-turn parity via the `"jobProjectId"` fallback, applied independently at this exact call site (`chat.rs`'s `generate_image` dispatch branch bypasses `execute_single_tool`, so it needs its own copy of the fallback) and at `execute_single_tool` for every other write tool. See §36.18 for the full mechanism and the Home-sentinel landmine this fix had to avoid.
