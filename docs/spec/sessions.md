# 30. Chat Sessions

> **Status:** BUILT (§30.1–30.11 BUILT)
> **Created:** 2026-07-08
> **ADRs:** ADR-0052 (session identity), ADR-0053 (compaction continuity)
> **Supersedes:** ai-integration.md §4.8.5 item 3 (thread_id column removal — see §30.8.4); the `chat_thread_{projectId}` reset-pointer pattern (§30.8.1)
> **Research:** docs/audits/2026-07-08-session-model-research.md
> **Amended:** 2026-08-16 — per-session agent binding (ADR-0062); phase-2 dispatch (ADR-0063)

Pane's first real session model. A **session** is a first-class, listable, switchable, hide-able chat thread scoped to a surface (a Project or Home). Sessions are Pane-owned identity, and each session **binds one agent at creation, immutably** (ADR-0062; §30.1.3). ⚠ *Supersedes the 2026-07-08 locked decision "provider resolved per-turn and never bound to a session": the agent half is reversed. Provider resolution:* in phase 1 the provider still resolves per-turn from the global mode, within the bound agent's class; under ADR-0063 it resolves from the bound agent's runtime (§30.7.1). Different agent = new session — there is no re-bind. Two surfaces only — Project and Home; folders share the parent project's session, with folder context arriving via system-prompt injection only (locked, 2026-07-08). Lifecycle at launch: **create / list / switch / hide / unhide / rename** *(rename amended in 2026-07-08, design pass)*. No destructive delete at launch (locked, 2026-07-08); delete is a post-launch decision with memory/extraction implications (§30.10).

## 30.1 Identity & schema

### 30.1.1 The `chat_sessions` table

New table, **not** in `CRR_TABLES` — chat is per-device, matching `chat_messages_local` (non-CRR) and the ADR-0022 per-device precedent.

```sql
CREATE TABLE IF NOT EXISTS chat_sessions (
 id TEXT NOT NULL PRIMARY KEY, -- UUID v4 for new sessions; legacy bucket value for migrated rows (§30.4)
 project_id TEXT NOT NULL, -- surface: project UUID | 'workspace' | '__recovered__' (migration-only, §30.4.3)
 title TEXT NOT NULL DEFAULT '', -- auto-generated by default; user-renameable via rename_session (§30.2.5)
 origin TEXT NOT NULL DEFAULT 'user', -- 'user' | 'migrated' | 'recovered' | 'spawn' | 'schedule' (§36.3.6)
 created_at TEXT NOT NULL DEFAULT (datetime('now')),
 last_active_at TEXT NOT NULL DEFAULT (datetime('now')),
 hidden_at TEXT, -- NULL = visible; soft-hide, never row deletion
 is_active INTEGER NOT NULL DEFAULT 0, -- exactly one per surface, DB-enforced below
 agent_id TEXT REFERENCES ai_agents(id) -- bound at creation, immutable; NOT NULL by contract post-migration (§30.1.3, ADR-0062)
);

CREATE UNIQUE INDEX IF NOT EXISTS idx_sessions_active_per_surface
 ON chat_sessions(project_id) WHERE is_active = 1;

CREATE INDEX IF NOT EXISTS idx_sessions_surface
 ON chat_sessions(project_id, last_active_at DESC);
```

`project_id` here means **surface**, and only surface. Its domain is a project UUID, the literal `'workspace'` (Home), or the migration-only sentinel `'__recovered__'`. Runtime session creation accepts only the first two — `'__recovered__'` can never be created after the v72 migration.

The active-session invariant — **exactly one active session per surface** — is enforced by the partial unique index, not by an `ai_settings` pointer and not by frontend discipline (mechanize over discipline). Switching is a demote-then-promote inside one transaction, mirroring the §24.7A `is_main` contract.

### 30.1.2 `chat_messages_local.thread_id` becomes load-bearing

The existing, always-NULL `thread_id` column (live schema verified: `migrations.rs::create_chat_tables`, last column; live DB confirmed 2026-07-08) becomes the **written foreign key to `chat_sessions.id`**:

- `save_chat_message` gains a required `thread_id` parameter and writes it on every INSERT. The current INSERT (`save_chat_message`, `ai::chat`) omits the column; that omission ends.
- Message loads key on `thread_id`, not `project_id` (§30.2.4).
- New index: `CREATE INDEX IF NOT EXISTS idx_chat_local_thread ON chat_messages_local(thread_id, created_at);`
- `chat_messages_local.project_id` reverts to meaning **the surface** — the project UUID or `'workspace'` — and nothing else. The pre-§30 conflation, where a reset stuffed a `pane-{uuid}` into `project_id`, ends (§30.4 re-points legacy rows).

No FK constraint is declared (SQLite FK enforcement is off in this codebase; consistency is by contract + migration + tests).

`chat_archive` (memory-pipeline §5.14.2) already carries `thread_id TEXT NOT NULL`, populated at archive time from the message record's `thread_id` field — which pre-§30 is an alias of the bucket key. Under §30.4's id-equality rule, existing archive rows are therefore **already correct** (their `thread_id` equals the migrated session's id) and need no touch. Forward, the archiver writes the real session id, which is the same field it reads today. *(Archiver write-path confirmation is an implementer apply-time check — see §30.8.3; the archiver source was not re-read this session.)*

### 30.1.3 Agent binding

`agent_id` is written **once, at INSERT**, on every creation path (§30.2.1, §30.2.6, and the lazy/fallback creates). **No update path exists** — immutability is mechanical, not guarded. A different agent means a new session (ADR-0062 D1).

**Creation-time resolution** *(amended 2026-08-17 — ADR-0062 Amendment: binding is assigned by initiator)*. **User-initiated:** `create_session` and the New Project dialog take `agent_id` from the picker (designated default preselected; in-class agents only while the global mode lives — §24.7C unchanged in phase 1). **Agent-initiated:** a `create_project` tool call binds the **acting agent**, resolved from the tool call's own session binding (the R1 `session_id` threading through the tool loop — no new plumbing), never the default. **System-initiated:** the two automatic paths — `get_active_session` lazy-create and `hide_session`'s last-visible fallback — bind the **designated default** with no UI: phase 1 the `is_main = 1 AND is_active = 1` row; under ADR-0063, `is_default` (agents.md §24.7A).

**Migration & backfill (ADR-0062 D3).** Additive nullable `ALTER`; backfill every existing row to the current main; if no `is_main = 1 AND is_active = 1` row exists, fall back to the most recently created active agent (`created_at DESC`); if zero active agents, NULL with self-heal. **Self-heal contract:** any post-migration reader encountering `agent_id IS NULL` resolves the designated default, writes it back, and logs `[SESSION] BINDING SELF-HEAL:` — the §30.2.6 lazy-safety-net posture applied to binding. This is the **only** sanctioned post-INSERT write to the column.

**Unavailable bound agent (derived read-only — ADR-0062 D5).** When the bound agent is outside the active provider class (phase 1 only) or `is_active = 0`, the session renders read-only: composer disabled, inline notice naming the bound agent, "Start new session" affordance (binds the designated default). The state is **derived per render, never stored** — nothing is written on the session, and it clears itself when the condition clears. Backend: `ai_chat_stream` against such a session errors explicitly, naming the bound agent — never silent re-bind, never dispatch through a different agent. Under ADR-0063 the class case disappears; the deactivated-agent and disconnected-runtime cases keep this exact treatment.

**Disconnect preserves the binding (D21, #2649).** Disconnecting a runtime (e.g. OpenClaw) **does not** NULL or reassign `chat_sessions.agent_id` — it only deactivates the affected `ai_agents` rows (`is_active = 0`). A session bound to a now-deactivated agent falls under the unavailable-bound-agent rule immediately above: dispatch errors explicitly naming the agent (`agents::check_bound_agent_active`, enforced in `resolve_runtime_config_for_session` before self-heal ever runs), and the composer renders read-only per `ReadOnlySessionNotice`/`SessionDropdownHeader`. The lock clears automatically — no session-side write required — the moment the agent is reactivated (e.g. by re-pairing, §22C), since the read-only state is derived from `is_active` on every render, not stored. The NULL self-heal path (`resolve_and_selfheal_session_agent`) remains scoped to genuinely NULL `agent_id` rows (legacy migration backfill) and is never triggered by disconnect.

**Lock banner renders on every surface, including Home (D22, #2649).** The read-only lock computation (bound-agent lookup + `is_active`/runtime-connectivity check) is surface-independent — it is derived from `chat_sessions.agent_id` and `ai_agents`, not from any project context. `SessionDropdownHeader` (project-scoped surfaces) and `ChatSidebar`'s Home path both call the same extracted helper (`sessionReadOnlyCheck.ts`) so the two surfaces can never disagree on whether a session is locked. Home does **not** mount `SessionDropdownHeader`/the header bar (that gate, `showHeader && $activeProject !== null`, stays — the clean Home look is unchanged); Home renders `ReadOnlySessionNotice` and disables the composer directly whenever its active session's bound agent is deactivated, exactly like any project-scoped session. `handleSendMessage`'s error handling recognizes the `check_bound_agent_active` deactivation message and surfaces it as the clear lock copy, not a generic "Something went wrong" bubble, for the race window before the banner mounts.

**Speaker-label resolution on Home, independent of the header (#2643).** `ChatPanel`'s speaker-label fallback (`message.agent_name ?? sessionBoundAgentName ?? 'Pane'`) previously sourced `sessionBoundAgentName` exclusively from `SessionDropdownHeader`'s `onBoundAgentChange` callback, which never fires on Home (the header never mounts there, same root cause as D22 above) — so live-streamed messages on Home labeled 'Pane' until the DB-sourced `agent_name` landed. `ChatSidebar` now resolves the Home session's bound agent name unconditionally via `resolveBoundAgent()` (the same pure helper the D22 lock check uses) and passes it to `ChatPanel` as `boundAgentNameProp`; `ChatPanel` derives `sessionBoundAgentName` from either the header callback (`showHeader = true`) or the prop (`showHeader = false`), mirroring the `readOnlyState`/`readOnlyStateProp` pattern exactly.

**Home-surface resolution is keyed off the thread id, not the session store (D22/#2643 follow-up).** Both notes above compute their state from "the Home session" — in practice, that resolution must be driven off `$activeChatThreadId`, not `$sessionStore.activeSession`. Nothing on Home writes to `sessionStore`: `SessionsDrawer.svelte` keeps its own local session list, and only the project-surface-only `SessionDropdownHeader` calls `sessionStore.loadSessions`. On a real Home launch, `$sessionStore.activeSession` is `undefined` when `ChatSidebar`'s Home `$effect` first fires; the thread only resolves afterward, via the NAV event (`pane-navigation-complete`, `navigation.ts`) setting `$activeChatThreadId`. `ChatSidebar`'s Home effect is keyed off `$activeChatThreadId` (re-running whenever NAV resolves or changes it) and calls `sessionStore.getActiveSession('workspace')` — the same `'workspace'` surface constant `loadOrCreateThread`/`navigateTo` already use for Home — to resolve the session, with a staleness guard (bail if the thread id changed again, or the resolved session's `id` doesn't match, while the lookup was in flight). `isFreshSession` and `resolveGreetingAgentName`'s bound-agent lookup elsewhere in `ChatSidebar.svelte` benefit from the same fix, since `getActiveSession` populates `$sessionStore.activeSession` as a side effect.

**Header.** The session header displays the bound agent (ADR-0062 D9); visual treatment is the design pass. Session surfaces do not listen for `pane-agent-switched` — the binding cannot change (§24.7B).

**Runtime identity on the wire (ADR-0067 D2).** The runtime config that `resolve_runtime_config_for_session` resolves for a session includes the bound agent's `ai_agents.runtime_ref` — this, and not the Pane-local `ai_agents.id`, is what identifies the agent to OC on every request the session dispatches. See `docs/spec/ai-integration.md` §4A.2.1.

## 30.2 Lifecycle & commands

All commands are Tauri commands, now split across `src-tauri/src/ai/{chat,ingest,scheduler,tools,connections}.rs` by responsibility (#3097; see `docs/architecture-cheat-sheet.md`'s module map), unless noted. The frontend wrapper layer is `src/lib/api.ts`, where `listChatThreads` already exists as a typed stub returning `[]` — it gets a real implementation.

### 30.2.1 `create_session(project_id, agent_id) → Session`

Creates a row with a fresh UUID v4, `origin='user'`, the given **agent binding** (§30.1.3 — picker at creation on Home and every project, designated default preselected), and atomically makes it the active session for the surface (demote-then-promote, one transaction). Returns the full Session record. The previous active session remains **visible** in the list — creating a session is non-destructive and fully reversible by switching back, which is what makes #395's accidental-click hazard structural history rather than a UX patch (§30.9, and the "#395 becomes" note).

A fresh session inherits full project/folder context automatically — context is rebuilt from DB state by `build_context_prompt` on every `ai_chat_stream` call and is never derived from chat history (verified: context assembly is per-call). No context-carrying work is needed; the cultivated agent keeps its grounding by construction (locked, 2026-07-08).

> **BUILT (PR 2, #3050):** `create_session` (the `#[tauri::command]`) is now a thin wrapper over `ai::chat::create_session_internal(conn, project_id, agent_id, origin, promote)`, called with `origin="user"`, `promote=true` — zero behavior change, zero call-site edits. Job sessions (§36.3.6) call the internal variant directly with `origin IN ('spawn', 'schedule')` and `promote=false`, which is the only way to create a row that is guaranteed to never become the active session for its surface. See `docs/spec/runtime.md` §36.3.6/§36.11.

### 30.2.2 `list_sessions(project_id, include_hidden) → Vec<Session>`

Sessions for one surface, `last_active_at DESC`. Default excludes hidden (`hidden_at IS NULL`); `include_hidden=true` includes them (the UI's "show hidden" affordance). Home lists `project_id='workspace'` and, grouped separately, `'__recovered__'` rows (§30.4.3).

> **BUILT (PR 2, #3050):** both branches of this query also filter `origin NOT IN ('spawn', 'schedule')`, regardless of `include_hidden` — the one sanctioned exception to §30.2.6 "surfaces are born-active." See `docs/spec/runtime.md` §36.11 ("a spawn session is never a surface").

> **PARKED (later PR):** Home's cross-project Scheduled panel reads `origin='schedule'` rows directly, not through `list_sessions` — that query doesn't exist until §36.3.8's UI PR.

### 30.2.3 `switch_session(session_id) → Session`

One transaction: `UPDATE chat_sessions SET is_active=0 WHERE project_id = {target's surface} AND is_active=1;` then `UPDATE chat_sessions SET is_active=1, last_active_at=datetime('now'), hidden_at=NULL WHERE id = ?;`. Switching to a hidden session unhides it. The partial unique index makes a violated ordering a hard constraint error, not silent corruption.

### 30.2.4 Message load

`load_chat_messages` re-keys to `thread_id`: `WHERE thread_id = ?1` (plus the existing `after`/limit/offset shape). The command's parameter is a **session id**; the returned JSON `thread_id` field becomes the real column value rather than today's `project_id` alias. Navigation's thread-resolution step (`navigateTo` STEP 4 / `getOrCreateThread`) is replaced by **`get_active_session(project_id)`**: return the surface's `is_active=1` row; if none exists (fresh surface), create one (`origin='user'`, bound to the designated default — §30.1.3). The `getOrCreateThread` ai_settings lookup dance in `api.ts` is deleted (§30.8.1).

### 30.2.5 `hide_session(session_id)` / `unhide_session(session_id)`; titles

Hide sets `hidden_at=datetime('now')`. Hiding the **active** session activates the surface's most-recent visible session, creating one if none exists (a surface is never left without an active session). The UI enforces this proactively: Hide is disabled on the sole visible session for a surface, preventing the born-active fallback from firing in normal use. Unhide clears `hidden_at`. **Hide is a list-visibility concern only** — see §30.6 for what it does *not* do.

Titles are auto-generated by default and user-renameable at launch *(amended 2026-07-08, design pass — was post-launch)*. Auto-generation: first user message, truncated ~40 chars; while no message exists, the display fallback is `"Session {YYYY-MM-DD}"`. Rename is a new command, **`rename_session(session_id, title)`**: trims input and writes the existing `title` column on the `chat_sessions` row — no schema change. Precedence rule (mechanized, not conventional): **auto-titling writes only when `title = ''`**; any non-empty user title therefore permanently wins, because auto-title never fires again once the column is non-empty. Renaming to an empty/whitespace title resets `title=''`, reverting the session to auto-title behavior. UI affordance (inline click-the-name, … → Rename) is Claude Design's, downstream of this contract.

### 30.2.6 Surfaces are born-active, never born-empty

Every surface has an active session from the moment it exists — no manual "create first session" step, matching the design's fresh-session state. Two mechanisms, both required:

- **Eager:** creating a new Project auto-creates its first `chat_sessions` row in the same flow — active, `origin='user'`, empty title (auto-title fallback displays), chatbox live, **bound by initiator** (§30.1.3; ADR-0062 Amendment 2026-08-17): the New Project dialog's agent picker (default preselected) when user-created, the acting agent when created by the `create_project` tool. *(Hook location in the project-creation command: implementer-confirm at apply — that path was not read this session.)*
- **Lazy safety net:** `get_active_session`'s create-if-none (§30.2.4) remains, and is the guarantee for surfaces with no creation event — Home always has an active `'workspace'` session (fresh installs get one on first visit; migrated installs get one from §30.4 step 3), and any legacy or edge surface self-heals on first access.

The invariant both mechanisms serve: **`get_active_session(surface)` never returns nothing.**

> **Corrected 2026-10-28 (#3050 fix PR, live-test #1, Bug 2).** This invariant held for the `get_active_session` *command* itself, but `ai::chat::ai_chat_stream`'s own `session_id: None` fallback (chat.rs) carried an independent, INLINE half-copy of the same SELECT — the lookup half only, with no create-on-miss half — that violated this exact invariant for its own call path: a miss resolved via `.unwrap_or(project_id_ctx)` to the literal, non-existent string `"workspace"` (or whichever `context.projectId` string was supplied) instead of creating a real row. That fabricated id then propagated into `agent_jobs.origin_session_id` and `chat_messages_local.thread_id` for any tool call made during that turn (observed via the schedule-family confirmation chip: written with no error — no FK on `chat_messages_local.thread_id` — into a thread nothing ever renders, surviving quit/reopen). **Fixed by extracting the create-on-miss half into a shared `get_or_create_active_session_id(conn, project_id)`, called by BOTH `get_active_session` and `ai_chat_stream`'s fallback** — one resolution, not two independently-maintained half-copies that can drift out of sync with this invariant. `ai_chat_stream` now surfaces a real `Err` on a genuine resolution failure (lock poisoned, DB error) rather than ever substituting a sentinel string that looks like a valid id. Separately, defense-in-depth: `ai::scheduler::insert_schedule_confirmation_message`/`insert_job_brief_message` (the two Pane-written synthetic message writers) now refuse an unknown `thread_id` outright (`require_known_thread_id`) rather than relying solely on this invariant holding upstream.

## 30.3 Surfaces: Project and Home

Same model, different surface key. Home is `project_id='workspace'` — it gets New Chat and the session list exactly as projects do. The ChatPanel guard hiding New Thread for `'workspace'` and `'__global__'` (`ChatPanel.svelte:482`, live-verified) and `reset_chat_thread`'s project-only contract are superseded (§30.8).

**Settings hosts no sessions and no chat (#2536, 2026-08-16).** `'__global__'` — never a recognized spec surface — is retired as a chat surface key: ChatPanel does not mount in Settings, and no session may carry `project_id = '__global__'`. The runtime surface set is closed at two: Project (UUID) and Home (`'workspace'`). Any legacy `'__global__'` sessions/messages are handled by the #2536 build (hidden under Home per the `'__recovered__'` precedent, or confirmed-empty — implementer-verify which state exists). No per-folder sessions: folder views show the parent project's active session; folder context is prompt injection only (locked).

## 30.4 Migration (v71→v72)

New arm in `migrations.rs` per the ADR-0017/0019 per-version-pair model; the v72 step is appended to every terminal arm (version-coverage test enforces completeness). `SCHEMA_VERSION` `"71"` → `"72"`. All steps idempotent.

**The id-equality rule that collapses this migration:** every legacy message bucket becomes a session whose **`id` equals the legacy bucket value**. Consequences: message backfill is a straight column copy; `compaction_summaries.thread_id` values already equal their session's id (ADR-0053 — zero compaction migration); `extraction_queue` needs no touch; `chat_archive` rows are already correct (§30.1.2); and the OC gateway session key for never-reset projects is byte-identical before and after (§30.7.2).

Ordered steps:

1. **Normalize the empty bucket.** `UPDATE chat_messages_local SET project_id='workspace' WHERE project_id='';` (rows predating the workspace literal).
2. **Create table + indexes** (§30.1.1 DDL).
3. **Seed sessions** — one per `SELECT DISTINCT project_id FROM chat_messages_local`, `INSERT OR IGNORE`, `id = bucket`, classified:
 - bucket `'workspace'` → surface `'workspace'`, `origin='migrated'`, active.
 - bucket matches `projects.id` → surface = itself, `origin='migrated'`. Active **unless** an `ai_settings` key `chat_thread_{bucket}` exists (a reset happened; the pointer's target is the active one).
 - bucket matches the **value** of some `chat_thread_{pid}` key → surface = that `pid`, `origin='migrated'`, **active** (this is the current post-reset generation).
 - remaining `pane-…` buckets (orphans from ≥2 resets ago; the pointer was overwritten and attribution is unrecoverable) → surface `'__recovered__'`, `origin='recovered'`, `hidden_at=datetime('now')`, title `"Recovered session"`. Surfaced under Home's list per §30.2.2 — reachable again, honoring the UI's long-standing "hidden (not deleted)" promise (`ChatPanel.svelte:484`).
4. **Backfill messages:** `UPDATE chat_messages_local SET thread_id = project_id WHERE thread_id IS NULL;`
5. **Re-point surface:** `UPDATE chat_messages_local SET project_id = (SELECT s.project_id FROM chat_sessions s WHERE s.id = chat_messages_local.thread_id) WHERE thread_id IN (SELECT id FROM chat_sessions);` — after this, `project_id`=surface holds for every row.
6. **Retire the pointer:** `DELETE FROM ai_settings WHERE key LIKE 'chat_thread_%';` (read in step 3, then removed — supersede, not extend).
7. Add `idx_chat_local_thread`.

Pre-migration backup runs per §2B.1; migration executes on the ADR-0051 separate short-lived connection like every other arm.

## 30.5 Compaction continuity (ADR-0053)

Forward rule: **every compaction read and write keys on the active session id.** The two `compaction_thread_id = project_id` sites in `ai_chat_stream` (trigger/count and post-summary filter — both live-verified) and `maybe_compact_thread`'s read/INSERT switch to the session id the frontend already threads through the call. `get_compaction_cutoff`'s parameter becomes a session id. Legacy summaries: zero migration by id-equality (§30.4).

A fresh session starts with fresh compaction state **by design** — that is the product feature ("start clean after many compaction cycles"), not a loss: project grounding arrives via context injection (§30.2.1), and the old session's summaries remain attached to the old session, intact on switch-back.

This also closes the live defect where compaction breaks entirely after a reset (§30.9 D3).

## 30.6 Extraction, FTS, search, memory — what "hidden" means

**Hide is list-visibility only.** A hidden session's messages: stay in `chat_messages_local`; stay reachable by `extraction_queue` jobs (worker fetches by `message_id` — session-model-indifferent, live-verified); stay in `chat_fts` (external-content FTS over the whole table, unscoped — live-verified) and thus in `search_memory`'s transcript pass; and extracted facts in `ai_memory` are untouched. Nothing about hiding excludes content from AI memory or search. Exclusion semantics belong to post-launch Delete and are explicitly **not** defined here (§30.10).

Forward contract: `extraction_queue.thread_id` carries the session id (the frontend already passes its active thread value to `ai_enqueue_extraction`; that value becomes the session id). Side effect of the §30.4 backfill: the worker's no-`user_message_id` fallback (`extraction_worker.rs:386–397`, `WHERE project_id=?1 AND role='user' AND thread_id=?2`) executes against real values for the first time — today it silently returns an empty user message on every use because `thread_id` is NULL on all rows (§30.9 D4).

## 30.7 Provider dispatch, session hints, canonical format

### 30.7.1 Dispatch contract — session → agent → runtime

**This subsection is the normative home of the primary-channel dispatch contract** (the role cross-references have called "§29"; the archived smart-model-routing-spec.md §29's live remnant for the internal channel is smart-routing.md §27.6 — untouched here per ADR-0061 D6).

Pane operates two channels. The **internal channel** (Smart Routing classifier + simple-tier, rerank, extraction, synthesis) is global, standalone-configured, and never session/agent/runtime-resolved — ADR-0061 D5/D6, normative at §27.6. The **primary channel** (chat) resolves per dispatch as:

`session.agent_id` → agent row → runtime.

- **Phase 1 (ADR-0062):** the bound agent supplies identity — context files (§24.7, ai-integration §29 items 11–12), daily-log workspace, attribution (§24.8), memory routing where session-scoped. The **provider and model still resolve from the global mode** (`AiConfig` + `ai_settings.model` + smart routing), within the agent's class; an out-of-class binding is the §30.1.3 read-only state, never a re-bind.
- **Phase 2 (ADR-0063):** the agent's `runtime_type` selects the connection (OC-gateway or API-direct, concurrently live); API-runtime agents dispatch their pinned `model`; OC agents' model resolves gateway-side exactly as today (#1453 decoupling preserved, per-agent form). No dispatch decision reads a global provider.

Smart routing composes with phase 2 unchanged in scope: classification stays global and, where it selects the simple tier, tier dispatch rides the internal connection — never the session's runtime (ADR-0061 D5/D6).

### 30.7.1a Session binding for internal/synthesis callers (D26/PR-B, #2673)

§30.1.3 documents three binding-initiator classes for a session's `agent_id` — user-, agent-, and system-initiated. There is a **fourth class**, not previously named here: **internal, fire-and-forget synthesis callers** — code that dispatches through `ai_chat_stream` for a single, non-interactive generation task rather than as part of a listable chat session's normal turn-taking. The create-agent and onboarding seed-generation pipeline's `streamAndCollect` (`src/lib/onboarding/seedGeneration.ts`) is the canonical example: it synthesizes SOUL.md/MEMORY.md content for a newly created agent by making one `ai_chat_stream` call and collecting the streamed response, with no session ever surfaced in the UI.

**Rule:** callers in this class must explicitly create and pass a real, agent-bound session — via a `createWorkshopSession`-style helper (`src/lib/onboarding/workshopSession.ts`) that calls `create_session(project_id, agent_id)` (§30.2.1) — **before** dispatch, and must pass the resulting session id as `ai_chat_stream`'s top-level `sessionId` argument. This is **not optional and not a convenience** — it is the only correct mechanism for binding synthesis to the intended agent's runtime.

**Never rely on `ai_chat_stream`'s `context.projectId` fallback resolution for this class.** §30.2.4's `get_active_session(project_id)` path is deliberately last-resort: it resolves to *whichever session happens to be active* for that project surface, which may be bound to a different, older agent than the one synthesis is meant to seed. A caller that omits `sessionId` and only passes `context.projectId` gets that ambient fallback, not the newly created agent — this is exactly the defect closed by D26/PR-B (#2673): create-agent synthesis was dispatching through whichever runtime the ambient active session happened to be bound to, not the runtime the user had just picked for the new agent, confirmed via live logs showing dispatch through the wrong agent's runtime.

**Ordering invariant:** the session-creation call must be awaited and its id in hand *before* the synthesis call is invoked — not created afterward for a later, unrelated purpose (e.g. a follow-up review-chat step) and reused retroactively. See `docs/spec/onboarding.md`'s dated amendment to the "Agent-before-synthesis ordering invariant (#2634, D10)" note for the concrete before/after call-order fix in `AgentCreateOverlay.svelte` and `Onboarding.svelte`.

### 30.7.2 Provider session hints are optimizations, never session truth

The session IS Pane's thread. Live-verified dispatch (all four `AiProvider::OpenClaw` arms in `ai_chat_stream` — primary dispatch `:9222`, retry-same-provider `:9319`, fallback-to-primary `:9449`, summary/compaction streaming `:10337`): the server-side session hint is passed **only on the OpenClaw arms** (`Some(&thread_id)`); OpenRouter, Anthropic, Ollama, and Venice receive none. The OpenClaw arm is selected by `AiProvider` variant, never by `base_url.is_some()`; Venice also carries a `Some(base_url)` and must not match (ADR-0065 D1, ai-integration §4.3.4). The hint value is currently `format!("pane-{}", context.projectId)` — the *project* UUID, which means today's "New Chat" never resets the OC gateway-side session (§30.9 D5).

Forward rule: the OC hint becomes **`pane-{session_id}`**. Under ADR-0063 the hint applies to sessions whose agent's `runtime_type = 'openclaw'`; sessions on other runtimes pass no hint, as their providers do today. New session ⇒ new gateway session; switch ⇒ the corresponding one. By id-equality, never-reset projects keep a byte-identical hint across the migration — gateway continuity preserved with zero coordination. Compaction calls continue to pass no hint (existing behavior, correct). *§29 evidence note: the hint behavior is source-verified at the dispatch call sites (static); execution-log confirmation — gateway log showing the received session key — is assigned to the build's live test, per the intent-vs-execution rule.*

### 30.7.3 Canonical message format (requirement only)

**Requirement:** stored message history (`chat_messages_local.tool_calls` / `tool_results` and the frontend's accumulated turn state) is provider-neutral; a per-dispatch adapter translates to each provider's wire format (Anthropic `content_blocks` vs OpenAI-style `tool_calls`) at the `stream_*` boundary.

⚠ **Superseded (2026-08-16, ADR-0062/0063):** mid-session provider switching no longer exists — the binding is immutable and the runtime travels with the agent. The provider-neutral storage **requirement stands** (sessions on different runtimes coexist in one install and one message table). **Replacement acceptance criterion:** with tool-call/tool-result history present, (a) any session renders its full history correctly regardless of which runtime wrote it, and (b) under ADR-0063, sessions bound to agents on **any two different** runtimes of {OC, OpenRouter, Anthropic, Ollama} each complete a next turn in the same app run without a provider API error.

The adapter's internals — canonical shape, translation tables, storage encoding — are build-scope (locked out of this spec). No thread-model change is required for the switch itself (provider already resolves per-call; verified).

## 30.11 External message ingestion & proactive delivery (minimal slice)

> **Added:** 2026-08-23 — #2410 minimal slice. ADR-0062 Amendment 2026-08-23 (append-in ≠ dispatch-out).
> **Scope:** pull-based delivery of agent-initiated (out-of-turn) messages into open sessions. No real-time push, no offline queue, no unread state, no §19.7 nudge — all explicitly deferred (§30.11.6).

An agent on an external runtime can produce messages outside Pane’s request/response cycle (a cron-triggered send, a scheduled task completing). This section defines how those messages land in the session transcript: a provider-neutral **ingestion command**, a per-source **pull adapter** (OpenClaw transcripts first), and a **poll lifecycle** scoped to open, focused, OpenClaw-runtime sessions.

### 30.11.1 Ingestion command — provider-neutral by construction

**`ingest_external_messages(messages: Vec<ExternalMessage>) → IngestResult`**. Input is a list of externally-sourced messages; nothing in the contract references OpenClaw, `chat.history`, or any transport. A future Hermes adapter or scheduler feed calls the identical command with messages sourced differently.

Each `ExternalMessage` carries at minimum: target session id, source message id (dedup key, §30.11.2), role, content, timestamp, and source agent id. Batch semantics are per-message skip-not-abort: one message’s failure (missing session, dedup hit, binding mismatch) never blocks the rest of the batch. The result reports inserted / skipped / errored counts.

**Insertion is the greeting pattern: a direct `save_chat_message`-equivalent DB write.** No dispatch, no stream, no context assembly.

**INVARIANT (session-scoped): an external-message insert never triggers dispatch.** The ingestion path must be structurally incapable of invoking `ai_chat_stream` or any streaming code path — it performs transcript writes only. (Restates, as a forward constraint on new code, the verified current-state finding that no insert→dispatch coupling exists.)

### 30.11.2 Dedup

`chat_messages_local` gains a nullable `oc_message_id` column (generic external-source message id, named for its first consumer) with a **partial unique index** (`WHERE oc_message_id IS NOT NULL`). Ingestion inserts via `INSERT OR IGNORE`-equivalent semantics keyed on that index: re-ingesting an already-seen batch inserts zero rows. Messages arriving without a source id insert with NULL (excluded from the index, never deduped — acceptable for this slice). Ships as a schema migration per policy (external installs exist; real migration arm required).

### 30.11.3 Source resolution — by key, never by cached session id (OC adapter)

The OC transcript pull adapter resolves the OC-side session **key** fresh on every poll cycle. It never caches or reuses a previously-observed OC `sessionId`: OC mints a new sessionId under a stable key whenever an out-of-turn send lands on a key with no live entry (rotation — empirically confirmed 2026-08-23), so any cached id is exactly the value that goes stale.

**Key derivation (verified 2026-08-23):** the OC session key for an OpenClaw-runtime session is the composite
`agent:{runtime_ref}:openai-user:pane-{session_id}`
where `runtime_ref` is the bound agent’s `ai_agents.runtime_ref` (e.g. `main`) and `session_id` is `chat_sessions.id`. A pure function of data Pane already holds — **no new column tracks it.** (The bare `pane-{session_id}` dispatch hint is a component of this key, not the key itself; the bare form does not resolve.)

The adapter fetches recent messages via the gateway transcript route (fixed per the prerequisite PR — see sync.md §22C.6.5.6 note), with **no `since`/`before` cursor**: it over-fetches a small recent page and lets §30.11.2 dedup discard the already-seen. “Last known message id” tracking is deliberately not built in this slice. A gateway 502 or transport failure skips the cycle gracefully — log, return cleanly, retry next tick.

### 30.11.4 Poll lifecycle

> **Status: REMOVED, see §36.6** (PR 7, #3050). The frontend three-gate poll described below (open + focused + OC-bound) no longer exists — `ai::scheduler::run_oc_background_pickup` pulls every OC-bound session on the scheduler's own 60s tick regardless of open/focus state; Pane being open is the only requirement. The paragraphs below describe the PRE-PR-7 mechanism for historical context only.

A 60-second poll ran **only** while a session was (a) open (the surface’s active, rendered session), (b) app-focused, and (c) bound to an `runtime_type = 'openclaw'` agent. Backgrounding the app or switching away stopped the poll. Non-OpenClaw sessions never polled (nothing to pull; future sources add their own adapters and gating). Newly-ingested messages for the open session appended to the rendered transcript in order (now: via the `pane-oc-message-ingested` event, §36.6).

Sessions that were not open did not poll or receive messages — an out-of-turn message to a closed session landed on its next open. §36.6's background pickup closes most of this gap: a closed session with a recently-active OC agent now receives messages via the §36.7 `agent_message` notification path instead of waiting for next-open. Multi-session unread badges and the §19.7 nudge remain the deferred awareness layer (§30.11.6).

### 30.11.5 Binding, delivery, and the append-in / dispatch-out rule

Ingested messages are attributed to the session’s bound agent (the poll runs against one already-resolved session, so the source agent is unambiguous by construction; the adapter carries a defense-in-depth binding-mismatch skip for future multi-source use).

**Append-in ≠ dispatch-out (ADR-0062 Amendment 2026-08-23):** a session bound to a locked (inactive) or out-of-class agent still **accepts** ingested messages from that agent — delivery is transcript history, not agent action. Only *dispatch* remains refused per ADR-0062 D5. A user can therefore read what a since-locked agent sent without Pane ever dispatching through it.

`last_active_at` is **not** bumped by ingestion in this slice — user messages do not bump it today either; ingestion matching that behavior keeps the column’s semantics consistent. A future slice defining activity semantics revisits both together.

### 30.11.6 Non-goals (this slice)

Real-time push; offline queue; unread state/badges; §19.7 nudge integration; multi-session background polling; `since`-cursor pagination; session-creation on binding mismatch; `last_active_at` semantics. Each deferred explicitly — none are implied by this section’s mechanisms.

### 30.11.7 Stateful echo suppression — tombstoning (BUILT, #2410)

> **Added:** 2026-08-24 — #2410 tombstoning addendum, refined per Reed's scope audit (`docs/audits/2026-08-24-tombstone-scope.md` §6).

The §30.11.4 PR 4 content-match backstop (`is_recent_local_assistant_echo`) is **stateless**: it only ever compares an incoming message against the single most-recent local assistant row for the thread. Once that row is superseded (by the echo's own insert, or by any subsequent genuine insert), the classification is lost — a previously-caught echo can silently resurrect as a duplicate insert 1-2 poll ticks later (the "tick-3 leak"). Migration v86 adds `chat_oc_tombstones (thread_id, oc_message_id, reason, tombstoned_at)`, PK `(thread_id, oc_message_id)`, per-device (not in `CRR_TABLES`, matching `chat_messages_local`'s own scope), plus `idx_chat_local_thread_role_ts` on `chat_messages_local(thread_id, role, created_at DESC)`.

Two checks now run in `pull_oc_transcript_for_session`, **unconditionally on every poll tick** — including `suppress_ingest=true` ticks. This does not violate §30.11.4's defer-not-skip rule: both checks only ever resolve messages already permanently settled one way or another (already ingested, or already correctly classified as an echo); neither can ever cause a genuinely-deferred message to be dropped.

**Rule 1 — permanence pre-filter.** Before anything else, drop any incoming message whose `(thread_id, oc_message_id)` already has either a real `chat_messages_local` row or a prior `chat_oc_tombstones` row. This is what makes classification permanent — a settled id never reaches the drifting single-row comparison again. **This rule is unchanged by §30.11.10 and remains the primary id-based dedup mechanism.**

**Rule 2 — content-containment, LOG-ONLY as of §30.11.10 (#3053 item F).** For messages surviving Rule 1: (a) staleness gate — skip entirely if the message's own claimed `timestamp` is under 15 minutes old (fresh messages never reach this check); (b) a 20-character content-length floor — short boilerplate is never trusted enough to act on even if stale; (c) a ±5-minute containment query anchored on the incoming message's OWN `timestamp` (never wall-clock "now") against local assistant rows in that window. **Before §30.11.10, a substring match here tombstoned the message as `stale_echo` and dropped it. It no longer does either** — see §30.11.10 for why and what changed. The containment check and its age/length-floor logic are otherwise unchanged (still useful as a logged diagnostic signal).

The 150s content-match backstop (`is_recent_local_assistant_echo`, §30.11.4 PR 4 Candidate 3) is likewise **log-only as of §30.11.10** — a hit used to tombstone as `backstop_echo` and drop the message; it no longer does either.

Every tombstone write logs `[OC-PULL-TOMBSTONE] thread=... oc_msg_id=... reason=... content_preview="..."` (plus `matched_local_created_at` for prior `stale_echo` writes — historical only, see §30.11.10). `OcPullResult` carries `already_classified_count` (Rule 1, still a real drop count) and `stale_echo_tombstoned_count`/`content_match_skipped_count` (Rules 2/backstop — **as of §30.11.10, these count LOGGED OBSERVATIONS, not drops**; both field names are retained for API continuity though their meaning changed).

### 30.11.8 Ingest ordering — origination timestamp, floor clamp, tiebreak, compaction cutoff (BUILT, #2690)

> **Added:** 2026-08-24 — #2690.

Before this fix, `insert_external_message` stamped `created_at` with `datetime('now')` at INSERT time — i.e. poll-tick arrival order, not the order the source agent actually sent the messages in. A batch of several OC messages sent seconds apart could land in the same poll tick and get stamped with near-identical or out-of-order local timestamps, scrambling their rendered order relative to when they were actually written. Four coordinated changes close this, keyed on one invariant: **`created_at` is presentational; `rowid` (insertion order) is the durable ordering/cutoff key.**

**Origination-timestamp stamping.** `stamp_origination_timestamp()` (`ai::ingest`) stamps `created_at` from the `ExternalMessage.timestamp` the source adapter supplied (chrono-normalized to SQLite's `YYYY-MM-DD HH:MM:SS` format — never the raw RFC3339 string OC returns) instead of `datetime('now')`. A batch is pre-sorted by origination timestamp before insertion, so same-tick messages insert in the order they were actually sent, giving `rowid` a meaningful correlation with true send order within a batch.

**Floor clamp.** Clock skew between Pane's host clock and the source agent's clock (or a source agent backdating a timestamp) could otherwise let a reply sort *before* the message that triggered it. `stamp_origination_timestamp()` clamps the stamped value to `MAX(origination_timestamp, thread_max_created_at)` — the thread's current maximum `created_at` at insert time — so an ingested row can never sort earlier than the latest message already in that thread. A reply never renders above its own trigger, regardless of clock skew.

**Display tiebreak.** Two rows sharing the same stamped `created_at` (same-second collisions, common with the floor clamp active) are otherwise ordered arbitrarily by SQLite. `load_chat_messages`'s query is `ORDER BY created_at DESC, rowid DESC` — `rowid` (monotonic insertion order) resolves same-second ties deterministically, matching the pre-sorted batch order above.

**Compaction cutoff.** Compaction previously recorded `compacted_before` as a `created_at` string and filtered already-compacted messages by comparing `created_at < compacted_before`. Because origination-stamped rows can carry a `created_at` earlier than a compaction that already ran (a late-arriving message whose true send time predates the compaction boundary), that comparison could silently classify a never-compacted row as already-compacted and exclude it from context — a silent content loss, not an error. Migration v87 adds `compaction_summaries.compacted_before_rowid INTEGER`; the cutoff now compares each message's `rowid` against `compacted_before_rowid` (insertion order, immune to origination-timestamp skew) when present. Legacy compaction rows written before v87 have `compacted_before_rowid IS NULL` and fall back to the old `created_at`-keyed comparison — no migration of historical data, no behavior change for pre-existing rows.

6 tests in `ordering_2690_tests` (`src-tauri/src/ai/ingest.rs`) cover: same-tick batch rendering in true origination send order, `created_at` stored in SQLite format (not raw RFC3339), the clock-skew floor clamp, an empty-thread edge case (no prior max to clamp against), the compaction-boundary rowid cutoff (an origination-stamped row that would be wrongly excluded under the old `created_at` comparison is correctly retained), and `ORDER BY created_at DESC, rowid DESC` tiebreak determinism under repeated queries. (Relates to #2690, spec-covered-by: this section)

### 30.11.9 Identity-based own-turn tombstoning (BUILT, #2738)

> **Added:** 2026-08-26 — #2738. Source-scope audit: `docs/audits/2026-08-26-issues-2738-2739-source-scope.md`.

§30.11.7's Rule 2 (content-length floor, 20 chars) leaves a gap: Pane's **own** dispatch can itself produce a short assistant reply (e.g. a 4-character live reply like "Gold") that later echoes back through the OC poll as if it were a genuinely new proactive message. Content-based checks structurally cannot distinguish a short own-reply echo from a short genuine delivery of the same length — there is no length threshold that admits one and excludes the other. This section adds a THIRD, **identity-based** check that closes that gap without relying on content length at all.

**Guarantee this relies on (Task 1 of the audit, CONFIRMED):** OC serializes all turns on one session. Two independent OC-side mechanisms enforce this — `beginSessionWorkAdmission`'s scoped admission lock (the path Pane's own `POST /v1/chat/completions` dispatch goes through) and `replyRunRegistry`'s one-active-run-per-`sessionKey` guard (the auto-reply/channel-dispatch lane, also load-bearing for cron/proactive) — plus a third, structural backstop: every transcript append is serialized through a per-file FIFO queue + write lock, and `chat.history`'s `__openclaw.seq` is assigned by file-append position, so seq numbers physically cannot interleave even under a hypothetical registry race. **Consequence:** all `seq` values a turn produces are strictly less than all `seq` values the NEXT turn on that session produces — a `seq` baseline recorded immediately before a dispatch, compared against `seq` after that dispatch completes, exactly identifies "this dispatch's own output," with no risk of also catching a different turn's genuine output.

**Mechanism.** Two new functions in `src-tauri/src/ai/ingest.rs`, both calling the same gateway route §30.11.3 already uses (`GET /v1/sessions/:id/messages`) and both re-deriving the OC session **key** fresh from `runtime_ref`/`session_id` on every call (never caching OC's own internal, rotatable `sessionId` — same convention as §30.11.3's adapter):

- **`fetch_oc_latest_seq`** — called as the first statement inside `ai_chat_stream`'s spawned task, before the loop's first outbound OC call. Issues one `chat.history?limit=1` fetch and returns the newest message's `__openclaw.seq` as the dispatch's baseline. OpenClaw-runtime dispatches only (`is_openclaw`); other providers never touch an OC transcript and get no baseline. Best-effort: any failure (gateway unreachable, no history yet, session not OC-eligible) returns `None`, which simply skips the tombstone pass for that one dispatch — §30.11.7's existing content-based checks remain the fallback, exactly as before this fix shipped.
- **`tombstone_own_turn`** — called at **every** `ai_chat_stream` terminal `done:true` emit site (three total: the no-tool-calls success path, the reconnect-budget-exhausted error path, and the iteration-cap/no-progress-timeout fallback path (#3053 D+E renamed the latter from wall-clock) — an aborted or errored turn that produced partial output must still tombstone its own echoes, not just a clean completion). Re-fetches `chat.history?limit=20` (the same page §30.11.3's poll adapter reads) and, for every **assistant-role** message whose `__openclaw.seq` is strictly greater than the recorded baseline, writes a `chat_oc_tombstones` row via the existing `write_tombstone` helper with `reason="own_turn"` — a new reason string alongside `backstop_echo`/`stale_echo` (§30.11.7). Also best-effort: any failure logs and returns 0 tombstoned, never propagates into `ai_chat_stream`'s own response to its caller.

**Session-id rotation (Task 1, exception #3 of the audit).** OC can rotate its internal `sessionId` under a stable `sessionKey` mid-turn (a reset-triggered rollover). Because both functions re-derive the OC session **key** fresh from `runtime_ref`/`session_id` on every independent call — never caching or carrying forward OC's own rotatable `sessionId`, nor any transcript snapshot from a prior call — a rotation between the baseline fetch and the tombstone-pass fetch is transparent: each call simply resolves whatever `chat.history` returns for that stable key at the moment it runs.

**Ordering vs. §30.11.4/§30.11.7.** Because the permanence pre-filter (Rule 1, §30.11.7) already runs unconditionally, before `suppress_ingest` and before any content-comparison, an `own_turn` tombstone written by this pass is effective on the very next poll tick regardless of grace-window state — no interaction with §30.11.4's suppress-ingest mechanism is required for this fix to work. §30.11.7's Rules 1 and 2 remain untouched and continue to run for every message this identity-based check doesn't independently resolve (e.g. a dispatch whose baseline fetch itself failed).

**Storage.** In-memory only, scoped to local variables captured into the `ai_chat_stream` spawn closure (`own_turn_baseline_seq: Option<i64>`) — NOT a DB column and not a cross-dispatch cache keyed by session id. A baseline's entire lifetime is exactly one in-flight dispatch: recorded at dispatch start, consumed by that same dispatch's own tombstone-pass call(s), and dropped when the spawned task ends. This matches the audit's Task 3 recommendation and needs no cleanup/eviction logic since nothing outlives the closure.

4 tests in `own_turn_tombstone_tests_2738` (`src-tauri/src/ai/ingest.rs`) cover: a 4-character reply ("Gold") tombstoned by `tombstone_own_turn` and confirmed to never re-insert via a full round-trip through `pull_oc_transcript_for_session`; a genuinely new cron/proactive delivery arriving after a dispatch's tombstone pass (higher `seq`, never evaluated by that pass) still inserting normally; session-id rotation mid-turn producing a correctly fresh (never stale-cached) baseline on re-fetch; and the reconnect-budget-exhausted error path still tombstoning its own partial output exactly like the success path does. (Relates to #2738, spec-covered-by: this section)

### 30.11.10 Dedup is id/seq only — text containment downgraded to log-only, pre-existing text-based tombstones cleared (#3053 item F)

> **Added:** 2026-10-21 — #3053 item F. Scope doc: `~/Shared/ExampleApp/docs/audits/2026-10-20-scope-1061-fixes.md` ("The duplicate filter deletes real messages"). PR 2 of 4 on #3053.

**The incident.** On 2026-10-20, a genuine cron result (OC `seq` 154) was silently dropped. Root cause: an earlier assistant reply, already saved to `chat_messages_local`, happened to quote/restate the cron result's exact text (ordinary behavior — an agent acknowledging or repeating prior content is not an edge case). When the cron result's own OC pull ran, §30.11.7's Rule 2 (`check_stale_echo`) saw the LOCAL row's content contain the INCOMING message's content and classified it as `stale_echo`, tombstoning and dropping a message that was never actually duplicate. The 150s backstop (`is_recent_local_assistant_echo`) carries the identical structural risk for the same reason — substring containment is **correlation, not proof of duplication**. Quoting, restating, and repeated boilerplate are all normal, frequent behavior; any one of them can trigger a false containment match.

**The fix: dedup is id (§30.11.7 Rule 1) and seq (§30.11.9's `tombstone_own_turn`) ONLY.** Both text-containment checks (`check_stale_echo`, `is_recent_local_assistant_echo`) keep their exact containment/staleness/length-floor logic — unchanged, since the correlation signal is still useful for diagnosing suspected duplicates in logs — but a match no longer tombstones or drops a message. The call sites in `pull_oc_transcript_for_session` now log a `[OC-PULL]`-prefixed diagnostic line and the message proceeds to ingest exactly as if no match had occurred. No code path writes `reason='stale_echo'` or `reason='backstop_echo'` any more; `write_tombstone` remains in use only for the seq-based `reason='own_turn'` (§30.11.9), which is unaffected — removing text as a decision input does not weaken identity-based dedup, confirmed by `own_turn_tombstone_tests_2738` (unchanged, still green) and a dedicated guard test (`dedup_by_id_and_seq_tests_3053f::test_own_turn_echo_above_baseline_seq_still_tombstoned`).

**Clearing pre-existing damage: migration, not on-read.** A fix that only changes future classification leaves every message ALREADY wrongly tombstoned under the old text-based rules permanently invisible — §30.11.7 Rule 1's permanence pre-filter has no expiry and nothing else ever re-evaluates a settled id. Migration v92 (`migrate_v92`, `src-tauri/src/migrations.rs`) runs once, on the `v91→v92` schema transition, and executes `DELETE FROM chat_oc_tombstones WHERE reason IN ('stale_echo', 'backstop_echo')` — `own_turn` rows are left untouched (seq-based, correct, unrelated to this bug). Chosen over an on-read check for three reasons: (a) this is a genuine one-time cleanup of data written by behavior this same fix permanently removes — no code path can ever write one of these two reasons again, so there is nothing for a per-poll-tick check to keep guarding against; (b) it matches this file's own established convention for one-off data backfills/cleanups tied to a behavior change (e.g. §30.11.7's `migrate_v86` itself, §1.7.1's `migrate_v91` backfill); (c) it reuses the existing schema-version gate and pre-migration backup safety net every other version transition already has, rather than adding new per-tick-forever DELETE overhead. **Idempotency / second run:** the `DELETE ... WHERE reason IN (...)` is naturally idempotent (a second execution finds zero matching rows); the schema-version gate in `run_migrations` additionally ensures it only runs once per install in the normal upgrade path (once `schema_version` reaches "92", the "already matches" arm takes over). **Clearing the tombstone alone does not resurrect a message** — it only removes Rule 1's reason to drop the id on the next poll tick; because `pull_oc_transcript_for_session` has no `since`/cursor state (§30.11.3) and always re-fetches OC's small recent page, a cleared id reappears automatically the next time that session's page still contains it. If OC's own retention has since rolled the message out of the fetched window, there is nothing left to resurrect — an accepted, pre-existing limitation of this slice's no-cursor design.

**Tests** (`src-tauri/src/ai/ingest.rs`, `dedup_by_id_and_seq_tests_3053f` module, through the real `pull_oc_transcript_for_session`/`run_migrations` entry points, never a raw `INSERT` for the thing under test): two distinct OC messages where the second is a full quote of the first both land, neither tombstoned; the exact seq-154 incident shape (an earlier local reply quotes text a later, distinct cron result also carries) reproduced and confirmed landing; the seq-based own-turn guard proven directly (over-correction check — text losing its decision power must not weaken seq dedup); and a tombstone row seeded with `reason IN ('stale_echo','backstop_echo')` plus one `reason='own_turn'`, migrated via `run_migrations`, confirmed only the two text-based rows are cleared (own_turn survives), confirmed idempotent on a second run, and confirmed the previously-hidden message actually reappears via a real re-poll.
